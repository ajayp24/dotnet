1. Compute: ECS vs EKS vs Fargate vs Lambda

ECS — Elastic Container Service

AWS-native container orchestration. You define Task Definitions (container image, CPU, memory, env vars, IAM role) and run them as Services (long-running) or standalone Tasks (one-off jobs).

FeatureEC2 Launch TypeFargate Launch Type
Server managementYou manage EC2 instancesAWS manages all infra
Cost modelPay for reserved EC2 capacityPay per vCPU/memory/second
Startup timeFast (containers on running EC2)Slightly slower (~10–30s)
Best forHigh throughput, cost optimization at scaleSimplicity, variable workloads

EKS — Elastic Kubernetes Service

Managed Kubernetes control plane. AWS handles etcd, API server, and upgrades. You manage worker nodes (EC2 or Fargate profiles). Choose EKS when your team already knows Kubernetes, you need Kubernetes-native features (Helm, custom CRDs, Istio), or multi-cloud portability matters.

Lambda — Serverless Functions

Event-driven, no container management. Key limits: 15-minute max, 10 GB memory, 1,000 default concurrent executions per region. Cold start problem affects .NET — first invocation after idle can take 100ms–2s.

Cold Start Mitigation for .NET Lambda: Use Provisioned Concurrency (keeps N instances warm), compile with Native AOT (drastic cold start reduction), minimize package size, and avoid slow static initializers.

Decision Matrix

ScenarioBest Choice
Containerized .NET API, team owns infraECS Fargate
Need Kubernetes ecosystem (Helm, Istio, CRDs)EKS
Max cost efficiency, heavy steady trafficECS on EC2
Event-driven, short-lived processingLambda
Batch jobs, infrequent heavy processingECS Fargate Tasks
Sub-100ms latency, no cold start toleranceECS Fargate (always-on)

Presigned URLs — C# Example

C# — NuGet: AWSSDK.S3 
public class S3Service
{
    private readonly IAmazonS3 _s3Client;

    public S3Service(IAmazonS3 s3Client) => _s3Client = s3Client;

    public string GeneratePresignedDownloadUrl(string bucket, string key, int expiryMinutes = 15)
    {
        var request = new GetPreSignedUrlRequest
        {
            BucketName = bucket,
            Key = key,
            Verb = HttpVerb.GET,
            Expires = DateTime.UtcNow.AddMinutes(expiryMinutes)
        };
        return _s3Client.GetPreSignedURL(request);
    }

    public string GeneratePresignedUploadUrl(string bucket, string key, int expiryMinutes = 10)
    {
        var request = new GetPreSignedUrlRequest
        {
            BucketName = bucket,
            Key = key,
            Verb = HttpVerb.PUT,
            Expires = DateTime.UtcNow.AddMinutes(expiryMinutes),
            ContentType = "application/octet-stream"
        };
        return _s3Client.GetPreSignedURL(request);
    }
}

C# — Reading from Secrets Manager at Startup

C# — NuGet: AWSSDK.SecretsManager 
// Extension method to inject secrets into IConfiguration
public static class SecretsManagerExtensions
{
    public static IConfigurationBuilder AddSecretsManager(
        this IConfigurationBuilder builder, string secretArn)
    {
        var client = new AmazonSecretsManagerClient();
        var request = new GetSecretValueRequest { SecretId = secretArn };
        var response = client.GetSecretValueAsync(request).GetAwaiter().GetResult();

        // Secret JSON: {"username":"admin","password":"p@ssw0rd","host":"db.internal"}
        var secret = JsonSerializer.Deserialize<Dictionary<string, string>>(response.SecretString)!;

        var configData = new Dictionary<string, string?>
        {
            ["ConnectionStrings:OrdersDb"] =
                $"Host={secret["host"]};Database=orders;Username={secret["username"]};Password={secret["password"]}"
        };

        builder.AddInMemoryCollection(configData);
        return builder;
    }
}

// Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Configuration.AddSecretsManager(
    secretArn: Environment.GetEnvironmentVariable("DB_SECRET_ARN")!
);

C# — Reading at Runtime with Caching

C# 
public class DatabaseConnectionFactory
{
    private readonly IAmazonSecretsManager _secrets;
    private readonly IMemoryCache _cache;

    public async Task<string> GetConnectionStringAsync()
    {
        return await _cache.GetOrCreateAsync("db-conn", async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);
            var response = await _secrets.GetSecretValueAsync(new GetSecretValueRequest
            {
                SecretId = "prod/orders/db",
                VersionStage = "AWSCURRENT"
            });
            var s = JsonSerializer.Deserialize<DbSecret>(response.SecretString)!;
            return $"Host={s.Host};Database={s.DbName};Username={s.Username};Password={s.Password}";
        });
    }
}

C# — SQS Consumer (BackgroundService)

C# — NuGet: AWSSDK.SQS 
public class InventoryQueueConsumer : BackgroundService
{
    private readonly IAmazonSQS _sqs;
    private readonly string _queueUrl;
    private readonly ILogger<InventoryQueueConsumer> _logger;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var response = await _sqs.ReceiveMessageAsync(new ReceiveMessageRequest
            {
                QueueUrl = _queueUrl,
                MaxNumberOfMessages = 10,
                WaitTimeSeconds = 20,     // Long polling — reduces empty responses
                VisibilityTimeout = 60
            }, stoppingToken);

            foreach (var message in response.Messages)
            {
                try
                {
                    // SNS wraps message in envelope
                    var envelope = JsonSerializer.Deserialize<SnsEnvelope>(message.Body)!;
                    var order = JsonSerializer.Deserialize<OrderPlacedEvent>(envelope.Message)!;

                    await ProcessInventoryAsync(order);

                    // Delete ONLY after successful processing
                    await _sqs.DeleteMessageAsync(_queueUrl, message.ReceiptHandle, stoppingToken);
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "Failed to process {MessageId}", message.MessageId);
                    // Do NOT delete — visibility timeout expires, message reappears
                    // After maxReceiveCount failures → moves to DLQ automatically
                }
            }
        }
    }
}
DLQ Strategy: Set maxReceiveCount: 3 on your SQS queue. After 3 failures, the message automatically moves to the DLQ. Create a CloudWatch Alarm on ApproximateNumberOfMessagesVisible > 0 on the DLQ → SNS → PagerDuty. Use a Lambda replayer to re-enqueue DLQ messages after fixing the bug.

C# — DynamoDB Low-Level API

C# — NuGet: AWSSDK.DynamoDBv2 
public async Task<OrderDetail> GetOrderDetailAsync(string orderId)
{
    var response = await _dynamoDb.QueryAsync(new QueryRequest
    {
        TableName = "OrdersTable",
        KeyConditionExpression = "PK = :pk",
        ExpressionAttributeValues = new Dictionary<string, AttributeValue>
        {
            [":pk"] = new AttributeValue { S = $"ORDER#{orderId}" }
        }
    });

    var detail = new OrderDetail();
    foreach (var item in response.Items)
    {
        var sk = item["SK"].S;
        if (sk == "METADATA")
            detail.Metadata = MapToOrder(item);
        else if (sk.StartsWith("ITEM#"))
            detail.Items.Add(MapToOrderItem(item));
    }
    return detail;
}

13. Scenario Questions & Answers

How do you deploy a .NET API with zero downtime?

Strategy 1 — ECS Rolling Update

1. Register new task definition (new Docker image tag) 2. ECS starts NEW tasks (maximumPercent: 200 = double capacity) 3. New tasks pass ALB health check (/health returns 200) 4. ECS drains OLD tasks (stops sending new requests, waits for in-flight) 5. Old tasks terminated once drained → Zero downtime: capacity never drops below 100% during deploy

Strategy 2 — Blue/Green Deployment

1. Deploy "green" ECS service (new code) alongside "blue" (current) 2. Register green tasks in new target group 3. ALB rule: 10% green, 90% blue ← watch error rates / latency 4. Gradually shift: 10% → 50% → 100% 5. Problem detected? Shift 100% back to blue in seconds 6. Confidence period passes → decommission blue

Database Migration — Expand/Contract Pattern

SQL — Backward Compatible Migration 
-- Phase 1: Add new column (nullable = backward compatible)
ALTER TABLE orders ADD COLUMN customer_email_new VARCHAR(255) NULL;

-- Deploy code that writes to BOTH old + new, reads from old

-- Phase 2: Backfill new column
UPDATE orders SET customer_email_new = customer_email
WHERE customer_email_new IS NULL;

-- Deploy code that reads from new, writes to both

-- Phase 3: Future release — drop old column
ALTER TABLE orders DROP COLUMN customer_email;
How do you scale your .NET API for high traffic?
Layered Scaling Strategy Layer 1: CDN (CloudFront) → Cache static assets, reduce origin load by ~70% → Eliminate requests that don't need backend Layer 2: Load Balancing (ALB) → Distribute across multiple AZs → Health check removes unhealthy instances automatically Layer 3: Compute (ECS Auto Scaling) → Target CPU at 70% (target tracking policy) → Scale out: 60s cooldown | Scale in: 300s cooldown → Min: 2 tasks (HA across AZs) | Max: 50 tasks Layer 4: Caching (ElastiCache Redis) → Cache: reference data, user sessions, expensive query results → Reduces DB load by 60–80% Layer 5: Database Read Replicas → Route all SELECT queries to read replicas → RDS Proxy for connection pooling (critical for burst traffic) Layer 6: Async Offload (SQS) → Non-critical work off the request path → Order confirmation email → SQS → worker (reduces API response time)
How do you secure secrets in AWS?
Never do this: Hardcode secrets in appsettings.json, Dockerfile ENV instructions, or environment variables passed in plain text.
Defense in Depth Layer 1: Code — No secrets in source → .gitignore secrets files → git-secrets pre-commit hook blocks accidental commits → AWS CodeGuru Reviewer scans for hardcoded credentials Layer 2: Secrets Manager → Store DB passwords, API keys, TLS certs → Auto-rotation every 30–90 days (Lambda function) → Old version available 24h during rotation window Layer 3: IAM Least Privilege (no access keys) → ECS Task Role has ONLY GetSecretValue on its own secrets → No hardcoded access keys — ever → Use STS AssumeRole for cross-account access Layer 4: KMS Encryption → Secrets Manager uses KMS CMK (not AWS-managed key) → Separate KMS keys per environment → Key policy: only specific roles can use decrypt Layer 5: Network → VPC Endpoint for Secrets Manager (traffic stays in AWS) → Security Group restricts which tasks reach the endpoint → No NAT Gateway traffic for secret retrieval Layer 6: Audit → CloudTrail logs every GetSecretValue call → CloudWatch Alarm on unexpected access patterns → AWS Config rule: no access keys older than 90 days
Walk me through your autoscaling strategy for workers processing an SQS queue.
Queue-Based Worker Autoscaling Metric: ApproximateNumberOfMessagesVisible (SQS queue depth) Target: 100 messages per worker task Formula: desired_tasks = ceil(queue_depth / 100) Examples: queue_depth: 0 → 1 task (minimum) queue_depth: 500 → 5 tasks queue_depth: 4800 → 48 tasks queue_depth: 9999 → 50 tasks (capped at maximum) Scale-out cooldown: 30s (respond fast — messages are piling up) Scale-in cooldown: 120s (drain carefully — don't kill mid-process) Full Architecture: [SQS Queue] ← orders placed by API | | (CloudWatch metric: ApproximateNumberOfMessagesVisible) ↓ [Application Auto Scaling] ↓ [ECS Service: order-workers] min:1, max:50 ↓ [.NET BackgroundService] — processes 10 msgs/batch, 20s long-poll ↓ [RDS / DynamoDB / downstream services]
