1. JWT Deep Dive

Structure

A JWT is three Base64URL-encoded segments joined by dots:

HEADER . PAYLOAD . SIGNATURE

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJ1c2VyMTIzIiwiZXhwIjoxN... . RSA_SIGNATURE

Header

JSON — Header
{
  "alg": "RS256",   // Algorithm: RS256 (asymmetric) or HS256 (symmetric)
  "typ": "JWT"
}
AlgorithmTypeKey RequiredBest For
HS256SymmetricShared secretSingle-service, internal use
RS256Asymmetric (RSA)Private (sign) + Public (verify)Distributed systems, third-party auth
ES256Asymmetric (EC)Private + PublicMobile/IoT — smaller key size
Pitfall

HS256 requires every service that validates tokens to know the secret. RS256 distributes the public key only — the auth server holds the private key exclusively.

Payload Claims

JSON — Payload
{
  "sub": "user-123",              // Subject — who the token is about
  "iss": "https://auth.myapp.com", // Issuer — who created the token
  "aud": "api.myapp.com",          // Audience — who should accept it
  "exp": 1723000000,               // Expiry (Unix timestamp) — VALIDATE
  "iat": 1722996400,               // Issued At
  "jti": "unique-token-id",        // JWT ID (for revocation tracking)
  "roles": ["admin", "editor"],    // Custom claims
  "email": "user@example.com"
}

JWT Validation Checklist

  • Signature — verify with the correct key
  • Algorithm (alg) — must match your whitelist; reject none
  • Expiry (exp) — token must not be expired
  • Not Before (nbf) — if present, must be in the past
  • Issuer (iss) — must match your expected issuer exactly
  • Audience (aud) — must include your API's identifier
  • Token Type — ID token is not an access token

Common JWT Attacks

Attack 1: alg:none Attack

Attacker changes "alg": "none" and strips the signature. Vulnerable servers skip validation.

Vulnerable 
// Trusting alg from the token itself
var token = handler.ReadJwtToken(raw);
string alg = token.Header.Alg;
// NEVER use this to pick your validator!
Safe 
// Always whitelist the expected algorithm
var p = new TokenValidationParameters
{
    ValidAlgorithms = new[] { "RS256" },
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = rsaPublicKey
};

Attack 2: HS/RS Confusion Attack

If a server accepting RS256 also accepts HS256, an attacker signs a token with the public key as the HMAC secret. The server validates it as HS256 using the public key and it passes.

Fix

Explicitly whitelist only the expected algorithm. Never auto-detect from the token header.

Access Token + Refresh Token Pattern

Client → POST /auth/login ← { access_token (15 min), refresh_token (7 days) } Client → API calls with access_token in Authorization: Bearer header // When access_token expires: Client → POST /auth/refresh { refresh_token } ← { access_token: new 15-min token } // Refresh tokens are stored server-side → can be revoked

C# — Generate and Validate JWT (RS256)

Safe — Complete Implementation 
// NuGet: Microsoft.IdentityModel.Tokens, System.IdentityModel.Tokens.Jwt
public class JwtService
{
    private readonly JwtSettings _settings;

    public string GenerateToken(string userId, string email, IEnumerable<string> roles)
    {
        using var rsa = RSA.Create();
        rsa.ImportFromPem(_settings.PrivateKeyPem);
        var credentials = new SigningCredentials(
            new RsaSecurityKey(rsa), SecurityAlgorithms.RsaSha256);

        var claims = new List<Claim>
        {
            new(JwtRegisteredClaimNames.Sub, userId),
            new(JwtRegisteredClaimNames.Email, email),
            new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
        };
        foreach (var role in roles)
            claims.Add(new Claim(ClaimTypes.Role, role));

        var token = new JwtSecurityToken(
            issuer: _settings.Issuer,
            audience: _settings.Audience,
            claims: claims,
            expires: DateTime.UtcNow.AddMinutes(15),
            signingCredentials: credentials);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }

    public ClaimsPrincipal? ValidateToken(string token)
    {
        using var rsa = RSA.Create();
        rsa.ImportFromPem(_settings.PublicKeyPem);

        try
        {
            return new JwtSecurityTokenHandler().ValidateToken(
                token,
                new TokenValidationParameters
                {
                    ValidateIssuerSigningKey = true,
                    IssuerSigningKey = new RsaSecurityKey(rsa),
                    ValidAlgorithms = new[] { SecurityAlgorithms.RsaSha256 },
                    ValidateIssuer = true, ValidIssuer = _settings.Issuer,
                    ValidateAudience = true, ValidAudience = _settings.Audience,
                    ValidateLifetime = true,
                    ClockSkew = TimeSpan.FromSeconds(30)
                }, out _);
        }
        catch (SecurityTokenException) { return null; }
    }
}

// Program.cs — Add JWT auth middleware
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://auth.myapp.com";
        options.Audience = "api.myapp.com";
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidAlgorithms = new[] { "RS256" },
            ClockSkew = TimeSpan.FromSeconds(30)
        };
    });

PKCE — For SPAs and Mobile Apps

Safe — Generate PKCE Challenge 
public static (string verifier, string challenge) GeneratePkce()
{
    var bytes = RandomNumberGenerator.GetBytes(96);
    var verifier = Base64UrlEncoder.Encode(bytes);
    var hash = SHA256.HashData(Encoding.ASCII.GetBytes(verifier));
    var challenge = Base64UrlEncoder.Encode(hash);
    // Send challenge in /authorize, send verifier in /token
    return (verifier, challenge);
}

Client Credentials (Machine-to-Machine)

Safe — .NET API Calling Downstream API 
// Manual client credentials token fetch
public class TokenService
{
    private readonly HttpClient _httpClient;

    public async Task<string> GetTokenAsync()
    {
        var response = await _httpClient.PostAsync(
            "https://auth.myapp.com/token",
            new FormUrlEncodedContent(new[]
            {
                new KeyValuePair<string, string>("grant_type", "client_credentials"),
                new KeyValuePair<string, string>("client_id", "my-service"),
                new KeyValuePair<string, string>("client_secret",
                    Environment.GetEnvironmentVariable("CLIENT_SECRET")!),
                new KeyValuePair<string, string>("scope", "downstream-api")
            }));

        var json = await response.Content.ReadFromJsonAsync<TokenResponse>();
        return json!.AccessToken;
    }
}

ID Token vs Access Token

Key Rule

ID Token — tells YOUR APP who the user is. Never send it to APIs. It is for your client only.
Access Token — send to APIs. APIs validate it, check scopes. May be opaque or JWT.

5. OWASP Top 10 (.NET Specifics)

A01:2021 Broken Access Control Critical

Most common OWASP vulnerability. Missing authorization checks let authenticated users access data they don't own.

Vulnerable — IDOR 
[Authorize]
[HttpGet("documents/{id}")]
public async Task<IActionResult> Get(int id)
{
    var doc = await _db.Documents.FindAsync(id);
    return Ok(doc); // Any user sees any doc!
Safe — Resource-Based Auth 
[Authorize]
[HttpGet("documents/{id}")]
public async Task<IActionResult> Get(int id)
{
    var doc = await _db.Documents.FindAsync(id);
    if (doc == null) return NotFound();

    var auth = await _authService.AuthorizeAsync(
        User, doc, DocumentOperations.Read);

    if (!auth.Succeeded) return Forbid(); // 403

    return Ok(doc);
}
Fix
  • Deny by default — no access unless explicitly granted
  • Authorize at every layer: controller, service, repository
  • Log all access denials with user ID and resource
A02:2021 Cryptographic Failures Critical

Storing passwords in plaintext or using weak algorithms (MD5, SHA1 without salt) makes password databases trivially crackable.

Vulnerable — MD5 Password 
// NEVER — MD5 is trivially crackable
var hash = MD5.HashData(
    Encoding.UTF8.GetBytes(password)
).ToHexString();
Safe — BCrypt
// NuGet: BCrypt.Net-Next string hash = BCrypt.Net.BCrypt.HashPassword( password, workFactor: 12); // ~300ms bool ok = BCrypt.Net.BCrypt.Verify(password, hash);

Why BCrypt/Argon2 and not SHA-256 for passwords? SHA-256 is designed to be fast — GPUs compute billions/second enabling brute force. BCrypt/Argon2 are intentionally slow with configurable work factors. They also include automatic salting.

A03:2021 SQL Injection Critical
Vulnerable — String Concat
// username = "' OR '1'='1" → all users // username = "'; DROP TABLE Users;--" var sql = $"SELECT * FROM Users " + $"WHERE Username = '{username}'"; await _db.Database.ExecuteSqlRaw(sql);
Safe — EF Core LINQ
// EF Core LINQ — always parameterized var user = await _db.Users .Where(u => u.Username == username) .FirstOrDefaultAsync(); // Raw SQL with interpolation (safe) await _db.Database.ExecuteSqlInterpolated( $"UPDATE Users SET Login={now} WHERE Id={id}");
EF Core Pitfall

ExecuteSqlRaw($"...{variable}") is VULNERABLE. Use ExecuteSqlInterpolated instead — it treats the interpolated values as SQL parameters, not string concatenation.

A05:2021 Security Misconfiguration High
Vulnerable — Dev Page in Prod
// Shows full stack trace to users! app.UseDeveloperExceptionPage();
Safe — Env-Specific Config
if (app.Environment.IsDevelopment()) app.UseDeveloperExceptionPage(); else { app.UseExceptionHandler("/error"); // Generic app.UseHsts(); } // /error returns generic 500 — no stack trace

Other misconfigurations: default credentials not changed, Swagger in production without auth, CORS set to AllowAnyOrigin.

A06:2021 Vulnerable and Outdated Components High
Shell — NuGet Audit

A07:2021 Identification and Authentication Failures High
Vulnerable — No Rate Limiting
[HttpPost("login")] public async Task<IActionResult> Login(LoginRequest r) { var user = await _userManager .FindByEmailAsync(r.Email); if (user != null && await _userManager.CheckPasswordAsync(user, r.Password)) return Ok(GenerateToken(user)); return Unauthorized(); // Allows unlimited brute-force attempts! }

builder.Services.AddIdentity<ApplicationUser, IdentityRole>(options => { options.Lockout.MaxFailedAccessAttempts = 5; options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15); options.Password.RequiredLength = 12; options.Password.RequireUppercase = true; options.Password.RequireNonAlphanumeric = true; });
A09:2021 Security Logging and Monitoring Failures Medium
Never Log These

Always Log These

A10:2021 Server-Side Request Forgery (SSRF) High

Server makes HTTP requests to URLs controlled by the attacker, potentially hitting internal services or cloud metadata endpoints (e.g., AWS 169.254.169.254 for IAM credentials).

Vulnerable
[HttpGet("fetch")] public async Task<IActionResult> Fetch( [FromQuery] string url) { // Attacker: url=http://169.254.169.254/ // /latest/meta-data/ → AWS IAM creds! var content = await _client.GetStringAsync(url); return Ok(content); }
Safe — Allowlist + IP Block
private static readonly HashSet<string> _allowed = new(StringComparer.OrdinalIgnoreCase) { "api.trusted.com", "data.public.com" }; public async Task<IActionResult> Fetch(string url) { if (!Uri.TryCreate(url, UriKind.Absolute, out var uri) || uri.Scheme != "https" || !_allowed.Contains(uri.Host)) return BadRequest("Not allowed"); var ips = await Dns.GetHostAddressesAsync(uri.Host); if (ips.Any(IsPrivateIp)) return BadRequest("Internal addresses blocked"); return Ok(await _client.GetStringAsync(uri)); } private static bool IsPrivateIp(IPAddress ip) { var b = ip.GetAddressBytes(); return b[0] == 10 || (b[0] == 172 && b[1] >= 16 && b[1] <= 31) || (b[0] == 192 && b[1] == 168) || (b[0] == 169 && b[1] == 254); // Metadata }

7. CSRF — Cross-Site Request Forgery

The attacker's site submits a form to your site using the victim's session cookie — the browser sends cookies automatically on any request.

ASP.NET Core Antiforgery

Vulnerable — No CSRF Protection
[HttpPost] public async Task<IActionResult> Transfer( TransferRequest request) { // Any site can POST here with victim's cookie! await _bankService.TransferAsync(request); return Ok(); }
Safe — Antiforgery Token
[AutoValidateAntiforgeryToken] // On controller [HttpPost] public async Task<IActionResult> Transfer( TransferRequest request) { // Token from hidden form field validated await _bankService.TransferAsync(request); return Ok(); } // Razor Form @Html.AntiForgeryToken() // Hidden input added

SameSite Cookie Attribute

Safe — Cookie Config
builder.Services.ConfigureApplicationCookie(options => { // Strict: cookie never sent cross-site (best CSRF prevention) // Lax: sent on top-level navigation only (links, not forms) // None: sent cross-site (requires Secure=true, use for OAuth) options.Cookie.SameSite = SameSiteMode.Strict; options.Cookie.SecurePolicy = CookieSecurePolicy.Always; options.Cookie.HttpOnly = true; });
Tip — JWT APIs

For JWT-based APIs where tokens are in the Authorization header: CSRF is not a concern — browsers do not automatically send custom headers. CSRF only applies to cookie-authenticated requests.

File Upload Security

Safe — Comprehensive File Validation
[HttpPost("upload")] public async Task<IActionResult> Upload(IFormFile file) { // 1. Size limit if (file.Length > 5 * 1024 * 1024) return BadRequest("Max 5 MB"); // 2. Extension whitelist (not blacklist) var ext = Path.GetExtension(file.FileName).ToLowerInvariant(); var allowed = new[] { ".jpg", ".png", ".pdf" }; if (!allowed.Contains(ext)) return BadRequest("Type not allowed"); // 3. Magic bytes — extension can be spoofed! var magicBytes = new Dictionary<string, byte[]> { [".jpg"] = new byte[] { 0xFF, 0xD8, 0xFF }, [".png"] = new byte[] { 0x89, 0x50, 0x4E, 0x47 }, [".pdf"] = new byte[] { 0x25, 0x50, 0x44, 0x46 } }; using var stream = file.OpenReadStream(); var header = new byte[4]; await stream.ReadExactlyAsync(header); if (!header.Take(magicBytes[ext].Length).SequenceEqual(magicBytes[ext])) return BadRequest("Content mismatch"); // 4. 12. Interview Q&A Rapid Fire

Interview Q
What's the difference between authentication and authorization?
Authentication = proving who you are (identity). Authorization = determining what you can do (permissions). JWT handles both: the token proves identity; claims/roles govern access. In .NET: [Authorize] enforces both.
Interview Q
Why is alg: none in JWT dangerous?
A library accepting none skips signature validation. An attacker crafts a token with any payload, strips the signature, sets alg: none, and the server accepts it. Fix: always whitelist the expected algorithm explicitly in ValidAlgorithms.
Interview Q
When would you choose RS256 over HS256?
RS256 when multiple services verify tokens — each only needs the public key. HS256 requires sharing the secret with every verifier. RS256 also guarantees only the auth server (holding the private key) can issue tokens.
Interview Q
What is PKCE and why does it exist?
SPAs and mobile apps can't safely store a client secret. PKCE replaces it with a one-time cryptographic challenge: the client generates a random verifier, hashes it into a challenge, sends the challenge in /authorize, then proves ownership by sending the verifier in /token. Even if the auth code is intercepted, it's useless without the verifier.
Interview Q
What's the difference between XSS and CSRF?
XSS = injecting JavaScript into a page to run in the victim's browser (attacks the client). CSRF = tricking the victim's browser into submitting a request using their credentials (attacks the server via the client). XSS can steal tokens; CSRF abuses existing sessions.
Interview Q
Why not store JWTs in localStorage?
Any JavaScript on the page — including injected XSS scripts — can read localStorage. httpOnly cookies cannot be read by JavaScript at all, making them immune to token theft via XSS.
Interview Q
Why use BCrypt/Argon2 instead of SHA-256 for passwords?
SHA-256 is designed to be fast — a GPU computes billions/sec enabling brute force. BCrypt/Argon2 have configurable work factors making each hash take 100-300ms. They also include automatic per-password salting, preventing rainbow table attacks.
Interview Q
What is SSRF and how do you prevent it?
Server-Side Request Forgery — the server makes HTTP requests to URLs the attacker controls, potentially hitting internal services, databases, or cloud metadata APIs (AWS IMDSv1: 169.254.169.254). Prevent with URL allowlists, blocking private IP ranges, and disabling IMDSv1 in favor of IMDSv2.
Interview Q
What does "defense in depth" mean?
Layering multiple independent security controls so that failure of any single layer doesn't compromise the system. Example: input validation + parameterized queries + WAF + least privilege DB user + field encryption + centralized monitoring + rate limiting.
Interview Q
What's the EF Core SQL injection pitfall most developers miss?
ExecuteSqlRaw($"...{variable}") looks like a safe interpolated string but is directly vulnerable. Use ExecuteSqlInterpolated instead — it uses FormattableString which EF Core converts to proper SQL parameters, not string concatenation.

13. OWASP Security Checklist for .NET APIs

Authentication & JWT

  • JWT signature validation enabled (not trusting alg from token)
  • Algorithm explicitly whitelisted — no none or auto-detect
  • Short expiry on access tokens (15–60 min)
  • Refresh token rotation implemented (old token invalidated on use)
  • Tokens stored in httpOnly; Secure; SameSite=Strict cookies
  • Minimal ClockSkew (30 seconds max)

Authorization

  • Every endpoint has [Authorize] or explicit policy
  • Resource-based authorization checks ownership
  • Deny by default — global fallback policy configured
  • Roles and claims validated server-side only
  • 403 returned for authorization failures (not 401)

Transport

  • HTTPS enforced with UseHttpsRedirection()
  • HSTS header configured in production
  • TLS 1.2+ minimum (TLS 1.0/1.1 disabled)
  • Security headers: X-Content-Type-Options, X-Frame-Options, CSP, Referrer-Policy

Input & Output

  • All input validated with whitelist approach (not blacklist)
  • No string concatenation in SQL queries — parameterized everywhere
  • HTML output encoded (Razor default; no @Html.Raw on user input)
  • File uploads: extension + magic byte validation, size limit, random filenames
  • Validation at system boundaries — never trust client-side validation alone

Secrets & Crypto

  • No secrets in code, appsettings.json, or git history
  • Secrets in Key Vault / Secrets Manager in production
  • Passwords hashed with BCrypt, Argon2, or PBKDF2 — not MD5/SHA1
  • Sensitive data encrypted at rest (TDE or field-level) and in transit (TLS)
  • Secret scanning configured (git-secrets, GitHub Advanced Security)

CSRF & CORS

  • Antiforgery tokens on all state-changing forms ([AutoValidateAntiforgeryToken])
  • SameSite=Strict on auth cookies
  • CORS policy is restrictive — no AllowAnyOrigin with AllowCredentials

Logging & Monitoring

  • Security events logged: failed logins, privilege escalation, unusual access patterns
  • No sensitive data in logs: passwords, tokens, PII, credit cards
  • Centralized logging with automated alerts (failed logins spike, privilege escalation)
  • Rate limiting on authentication endpoints (AddRateLimiter in .NET 7+)
  • Account lockout after failed attempts (ASP.NET Core Identity)

Dependencies & Configuration

  • dotnet list package --vulnerable runs in CI — build fails on high severity
  • Dependabot / NuGet Audit configured for automatic alerts
  • No debug endpoints (Swagger, health details) in production without authentication
  • Stack traces not exposed to users (UseExceptionHandler in prod)
  • Developer exception page disabled in production
