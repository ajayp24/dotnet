1. Indexes

Clustered Index

A clustered index defines the physical storage order of data rows. The leaf level of the B-tree is the actual data — there is no separate row lookup. Only one per table. The primary key creates one by default.

SQL — Clustered index via PRIMARY KEY
CREATE TABLE Orders (
    OrderID    INT            NOT NULL PRIMARY KEY,  -- Clustered by default
    CustomerID INT            NOT NULL,
    OrderDate  DATETIME       NOT NULL,
    Total      DECIMAL(10,2) NOT NULL
);

Non-Clustered Index

A separate B-tree structure whose leaf nodes hold the index key plus a row locator (the clustered key, or a RID for heaps). SQL Server follows the pointer to fetch the actual row. Up to 999 per table.

SQL — Non-clustered index
CREATE NONCLUSTERED INDEX IX_Orders_CustomerID
    ON Orders (CustomerID);

Covering Index

Includes all columns the query needs so SQL Server never revisits the base table. Extra columns are added via INCLUDE (not in the key — only in the leaf level).

SQL — Covering index eliminates Key Lookup
-- Query: SELECT OrderDate, Total FROM Orders WHERE CustomerID = 42
-- Without cover: Index Seek + Key Lookup per row (slow at scale)
-- With cover:    Index Seek only — zero extra I/O

CREATE NONCLUSTERED INDEX IX_Orders_CustomerID_Cover
    ON Orders (CustomerID)
    INCLUDE (OrderDate, Total);
Why use INCLUDE instead of adding columns to the key? INCLUDE columns only live in the leaf level, so they don't affect sort order or propagate through upper B-tree levels. The index key stays narrow, reducing its size and maintenance cost.

Composite Index — Leftmost Prefix Rule

A composite index is usable only when the query filters on the leading column(s) in order.

SQL — Composite index usage
CREATE NONCLUSTERED INDEX IX_Orders_CustomerDate
    ON Orders (CustomerID, OrderDate);

-- USES the index (leading column present)
SELECT * FROM Orders WHERE CustomerID = 5;
SELECT * FROM Orders WHERE CustomerID = 5 AND OrderDate > '2024-01-01';

-- Does NOT use the index efficiently (leading column missing)
SELECT * FROM Orders WHERE OrderDate > '2024-01-01';
Index DefinitionQuery PredicateUses Index?
(CustomerID, OrderDate)WHERE CustomerID = 5Yes
(CustomerID, OrderDate)WHERE CustomerID = 5 AND OrderDate = '2024-01-01'Yes (both)
(CustomerID, OrderDate)WHERE OrderDate = '2024-01-01'No
(OrderDate, CustomerID)WHERE OrderDate = '2024-01-01'Yes

When NOT to Index

Q: What is the difference between a clustered and non-clustered index?

A clustered index defines the physical row order — the leaf level is the data. One per table. A non-clustered index is a separate B-tree whose leaf nodes store the key plus a pointer back to the data row. Multiple non-clustered indexes are allowed. When a non-clustered index does not cover the query, SQL Server performs a Key Lookup to fetch remaining columns — expensive at scale.

Key Lookup Problem & Fix

SQL — Trigger and fix a Key Lookup
-- Index exists only on CustomerID
CREATE NONCLUSTERED INDEX IX_Orders_Cust ON Orders (CustomerID);

-- This query triggers a Key Lookup for OrderDate and Total on every row
SELECT CustomerID, OrderDate, Total
FROM   Orders
WHERE  CustomerID = 42;
-- Plan: Index Seek → Key Lookup × N rows  (bad at scale)

-- Fix: INCLUDE the missing columns
CREATE NONCLUSTERED INDEX IX_Orders_Cust_Cover
    ON Orders (CustomerID)
    INCLUDE (OrderDate, Total);
-- Plan: Index Seek only — no key lookups

Statistics — Why They Matter

SQL Server's optimizer uses statistics (column value histograms) to estimate row counts and choose join strategies. Stale statistics cause bad cardinality estimates, which lead to wrong join types and memory grants.

SQL — Update statistics
UPDATE STATISTICS Orders;          -- Single table
EXEC sp_updatestats;               -- All tables in current DB

-- View histogram for an index
DBCC SHOW_STATISTICS ('Orders', 'IX_Orders_CustomerID');
A Hash Join is not always bad — it is optimal for large unsorted inputs. It is a warning sign only when you see it on small tables, which indicates the optimizer has badly wrong row-count estimates (stale stats).

3. Deadlocks

A deadlock occurs when two transactions each hold a lock the other needs — a circular lock dependency. Neither can proceed.

SQL — Deadlock scenario and fix
CREATE TABLE Accounts (
    AccountID INT PRIMARY KEY,
    Balance   DECIMAL(10,2)
);
INSERT INTO Accounts VALUES (1, 1000.00), (2, 500.00);

-- Session 1 (Transaction A)
BEGIN TRAN;
    UPDATE Accounts SET Balance -= 100 WHERE AccountID = 1;  -- Locks row 1
    WAITFOR DELAY '00:00:05';
    UPDATE Accounts SET Balance += 100 WHERE AccountID = 2;  -- Waits for row 2

-- Session 2 (Transaction B) — run concurrently
BEGIN TRAN;
    UPDATE Accounts SET Balance -= 50 WHERE AccountID = 2;  -- Locks row 2
    UPDATE Accounts SET Balance += 50 WHERE AccountID = 1;  -- Waits for row 1 → DEADLOCK

-- FIX: always access rows in the same order (ascending AccountID)
-- Both transactions contend on row 1 first — one waits, no cycle
BEGIN TRAN;
    UPDATE Accounts SET Balance -= 100 WHERE AccountID = 1;
    UPDATE Accounts SET Balance += 100 WHERE AccountID = 2;
COMMIT;

Prevention Strategies

  • Consistent lock order — always access tables/rows in the same sequence across all transactions
  • Keep transactions short — minimize time locks are held
  • Add appropriate indexes — fewer rows touched per operation = fewer conflicts
  • Use SNAPSHOT isolation — readers never block writers
  • Retry on error 1205 — application-level retry for deadlock victims

SQL — Banking transfer with SNAPSHOT isolation
-- Enable at database level first
ALTER DATABASE BankDB SET ALLOW_SNAPSHOT_ISOLATION ON;

SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRAN;
    DECLARE @Bal DECIMAL(10,2);
    SELECT @Bal = Balance FROM Accounts WHERE AccountID = 1;

    IF @Bal >= 100
    BEGIN
        UPDATE Accounts SET Balance -= 100 WHERE AccountID = 1;
        UPDATE Accounts SET Balance += 100 WHERE AccountID = 2;
        COMMIT;
    END
    ELSE
    BEGIN
        ROLLBACK;
        RAISERROR('Insufficient funds', 16, 1);
    END
Q: SNAPSHOT vs READ COMMITTED SNAPSHOT (RCSI)?

SNAPSHOT isolation is transaction-scoped — snapshot is fixed at transaction start. RCSI is statement-scoped — each statement sees committed data as of that statement's start. RCSI is enabled with ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON and silently upgrades all READ COMMITTED sessions without code changes. Both use row versioning in TempDB.

5. CTEs (Common Table Expressions)

Regular CTE

SQL — Latest order per customer using CTE
WITH RecentOrders AS (
    SELECT CustomerID, OrderID, OrderDate, Total,
           ROW_NUMBER() OVER (
               PARTITION BY CustomerID
               ORDER BY OrderDate DESC
           ) AS rn
    FROM Orders
    WHERE OrderDate >= DATEADD(YEAR, -1, GETDATE())
)
SELECT CustomerID, OrderID, OrderDate, Total
FROM   RecentOrders
WHERE  rn = 1;

Recursive CTE — Employee Hierarchy

SQL — Recursive CTE: org chart traversal
CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    Name       NVARCHAR(100) NOT NULL,
    ManagerID  INT NULL REFERENCES Employees(EmployeeID),
    Title      NVARCHAR(100) NOT NULL
);
INSERT INTO Employees VALUES
    (1, 'Sarah Chen',  NULL, 'CEO'),
    (2, 'Mark Torres', 1,    'VP Engineering'),
    (3, 'James Liu',   2,    'Senior Engineer'),
    (4, 'Ryan Kim',    3,    'Engineer');

WITH OrgHierarchy AS (
    -- Anchor: root (no manager)
    SELECT EmployeeID, Name, Title, ManagerID,
           0 AS Level,
           CAST(Name AS NVARCHAR(MAX)) AS OrgPath
    FROM   Employees
    WHERE  ManagerID IS NULL

    UNION ALL

    -- Recursive: each direct report
    SELECT e.EmployeeID, e.Name, e.Title, e.ManagerID,
           h.Level + 1,
           h.OrgPath + N' → ' + e.Name
    FROM   Employees e
    INNER JOIN OrgHierarchy h ON e.ManagerID = h.EmployeeID
)
SELECT Level,
       REPLICATE(N'    ', Level) + Name AS IndentedName,
       Title, OrgPath
FROM   OrgHierarchy
ORDER BY OrgPath
OPTION (MAXRECURSION 50);
A CTE is not materialized by default — SQL Server may evaluate it multiple times if referenced more than once. For expensive CTEs referenced multiple times, use a temp table. Always set OPTION (MAXRECURSION n) for recursive CTEs; default limit is 100.

6. Window Functions

Ranking Functions

SQL — ROW_NUMBER, RANK, DENSE_RANK, NTILE
SELECT EmployeeID, DepartmentID, Salary,
       ROW_NUMBER() OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS RowNum,
       RANK()        OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS Rnk,
       DENSE_RANK()  OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS DenseRnk,
       NTILE(4)      OVER (PARTITION BY DepartmentID ORDER BY Salary DESC) AS Quartile
FROM   Employees;

-- Salaries: 100k, 90k, 90k, 80k
-- ROW_NUMBER:  1, 2, 3, 4  (always unique — arbitrary tiebreak)
-- RANK:        1, 2, 2, 4  (gaps after ties)
-- DENSE_RANK:  1, 2, 2, 3  (no gaps after ties)
-- NTILE(4):    1, 2, 3, 4  (divides into 4 equal buckets)

LAG and LEAD

SQL — LAG / LEAD for period comparisons
SELECT OrderDate, Total,
       LAG(Total, 1, 0)  OVER (ORDER BY OrderDate) AS PreviousTotal,
       LEAD(Total, 1, 0) OVER (ORDER BY OrderDate) AS NextTotal,
       Total - LAG(Total, 1, 0) OVER (ORDER BY OrderDate) AS DeltaFromPrev
FROM   Orders
WHERE  CustomerID = 42;

Aggregate Window Functions — Month-over-Month Growth

SQL — Running total + MoM growth
WITH MonthlySales AS (
    SELECT YEAR(OrderDate) AS Yr,
           MONTH(OrderDate) AS Mo,
           SUM(Total) AS Revenue
    FROM   Orders
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
)
SELECT Yr, Mo, Revenue,
       SUM(Revenue) OVER (
           ORDER BY Yr, Mo
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningTotal,
       LAG(Revenue) OVER (ORDER BY Yr, Mo) AS PrevRevenue,
       ROUND(
           (Revenue - LAG(Revenue) OVER (ORDER BY Yr, Mo))
           / NULLIF(LAG(Revenue) OVER (ORDER BY Yr, Mo), 0) * 100, 2
       ) AS MoMGrowthPct
FROM   MonthlySales
ORDER BY Yr, Mo;

7. PARTITION BY

SQL — Latest order per customer (deduplication)
WITH RankedOrders AS (
    SELECT CustomerID, OrderID, OrderDate, Total,
           ROW_NUMBER() OVER (
               PARTITION BY CustomerID
               ORDER BY OrderDate DESC, OrderID DESC  -- tiebreak
           ) AS rn
    FROM Orders
)
SELECT CustomerID, OrderID, OrderDate, Total
FROM   RankedOrders
WHERE  rn = 1;
SQL — First purchase date + stats per customer
SELECT DISTINCT
       CustomerID,
       MIN(OrderDate) OVER (PARTITION BY CustomerID) AS FirstPurchase,
       MAX(OrderDate) OVER (PARTITION BY CustomerID) AS LastPurchase,
       COUNT(*)       OVER (PARTITION BY CustomerID) AS TotalOrders,
       SUM(Total)     OVER (PARTITION BY CustomerID) AS LifetimeValue
FROM   Orders;

8. Pagination

OFFSET / FETCH

SQL — OFFSET/FETCH paging
DECLARE @Page     INT = 2;    -- 0-based
DECLARE @PageSize INT = 10;

SELECT OrderID, CustomerID, OrderDate, Total
FROM   Orders
ORDER BY OrderDate DESC, OrderID DESC
OFFSET  @Page * @PageSize ROWS
FETCH NEXT @PageSize ROWS ONLY;
OFFSET 1000000 ROWS forces SQL Server to read and discard 1 million rows before returning results. Performance degrades linearly with offset size.

Keyset Pagination (Cursor-Based)

SQL — Keyset pagination — constant performance
DECLARE @PageSize      INT      = 10;
DECLARE @LastOrderDate DATETIME = '2024-03-15 09:22:11';
DECLARE @LastOrderID   INT      = 50231;

SELECT TOP (@PageSize)
       OrderID, OrderDate, Total
FROM   Orders
WHERE  OrderDate < @LastOrderDate
   OR (OrderDate = @LastOrderDate AND OrderID < @LastOrderID)
ORDER BY OrderDate DESC, OrderID DESC;

Stable results (new rows)No — new rows shift pagesYes — anchored to a value
ComplexitySimpleRequires unique sortable key
Best forSmall/medium datasets, UI pagingInfinite scroll, datasets 10M+

9. Stored Procedures vs Inline Queries

Stored Procedures — Pros

  • Execution plan cached and reused
  • Reduced network traffic (one call)
  • Grant permissions on proc, not tables
  • Good for multi-step transactional logic

Stored Procedures — Cons

  • Parameter sniffing can cause bad plans
  • Logic split between DB and application
  • Harder to test and version-control
  • ORM tools work poorly with sprocs

Parameter Sniffing & Fixes

SQL — Parameter sniffing problem and three fixes
-- Problem: compiled for CustomerID=1 (1 row) — bad plan for CustomerID=100 (10k rows)
CREATE PROCEDURE GetOrdersByCustomer @CustomerID INT
AS BEGIN
    SELECT OrderID, OrderDate, Total FROM Orders WHERE CustomerID = @CustomerID;
END

-- Fix 1: OPTION(RECOMPILE) — recompile on each call (for infrequent variable queries)
SELECT OrderID, OrderDate, Total FROM Orders
WHERE  CustomerID = @CustomerID
OPTION (RECOMPILE);

-- Fix 2: Local variable — breaks sniffing; optimizer uses average estimate
DECLARE @LocalID INT = @CustomerID;
SELECT OrderID, OrderDate, Total FROM Orders WHERE CustomerID = @LocalID;

-- Fix 3: OPTIMIZE FOR UNKNOWN — uses average statistics, not sniffed value
SELECT OrderID, OrderDate, Total FROM Orders
WHERE  CustomerID = @CustomerID
OPTION (OPTIMIZE FOR (@CustomerID UNKNOWN));

10. Performance Tuning

SARGable vs Non-SARGable Predicates

SARGable (Search ARGument able) means the predicate lets the optimizer use an index seek.

Non-SARGable (Bad)SARGable Fix
WHERE YEAR(OrderDate) = 2024WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
WHERE UPPER(Name) = 'SMITH'WHERE Name = 'Smith' (case-insensitive collation)
WHERE CustomerID + 1 = 42WHERE CustomerID = 41
WHERE LEN(Notes) > 100Computed column + index, or avoid

Non-SARGable — Table Scan

SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

SARGable — Index Seek

SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01'
  AND OrderDate <  '2025-01-01';

Avoid Implicit Conversions

SQL — Implicit conversion kills index use
-- Column is INT, parameter is VARCHAR → implicit conversion, index ignored
DECLARE @ID VARCHAR(10) = '42';
SELECT * FROM Orders WHERE CustomerID = @ID;  -- BAD

-- Fix: matching types
DECLARE @ID INT = 42;
SELECT * FROM Orders WHERE CustomerID = @ID;  -- GOOD
Always specify column list — never SELECT *. Fetching all columns prevents covering indexes from working and increases network payload.

11. Coding Problems

1

Delete Duplicate Rows — Keep One

The Employees table has duplicate rows (same Name, Department, Salary). Keep the row with the lowest EmployeeID; delete all others.

SQL — Setup
CREATE TABLE EmpDupes (
    EmployeeID INT IDENTITY(1,1) PRIMARY KEY,
    Name       NVARCHAR(100) NOT NULL,
    Department NVARCHAR(100) NOT NULL,
    Salary     DECIMAL(10,2) NOT NULL
);
INSERT INTO EmpDupes (Name, Department, Salary) VALUES
    ('Alice',   'Engineering', 95000),
    ('Alice',   'Engineering', 95000),  -- duplicate
    ('Alice',   'Engineering', 95000),  -- duplicate
    ('Bob',     'Marketing',   72000),
    ('Bob',     'Marketing',   72000),  -- duplicate
    ('Charlie', 'HR',          65000);
SQL — Approach 1: CTE + ROW_NUMBER (preferred)
WITH Dupes AS (
    SELECT EmployeeID,
           ROW_NUMBER() OVER (
               PARTITION BY Name, Department, Salary
               ORDER BY EmployeeID    -- keep the lowest ID
           ) AS rn
    FROM   EmpDupes
)
DELETE FROM Dupes WHERE rn > 1;

-- Verify: 3 rows remain (Alice, Bob, Charlie)
SELECT * FROM EmpDupes;
SQL — Approach 2: Self-Join
DELETE e1
FROM   EmpDupes e1
JOIN   EmpDupes e2
    ON  e1.Name       = e2.Name
   AND  e1.Department = e2.Department
   AND  e1.Salary     = e2.Salary
   AND  e1.EmployeeID > e2.EmployeeID;  -- keep lower ID
CTE + ROW_NUMBER is preferred: more readable, handles 3+ duplicates cleanly, and you can verify by replacing DELETE with SELECT before committing. Self-join can become a cross-product on large tables with many duplicates.
2

Nth Highest Salary

SQL — Setup
CREATE TABLE SalaryTest (
    EmpID  INT IDENTITY PRIMARY KEY,
    Name   NVARCHAR(100),
    Salary DECIMAL(10,2)
);
INSERT INTO SalaryTest (Name, Salary) VALUES
    ('Alice',  120000),
    ('Bob',    110000),
    ('Charlie',110000),  -- tie with Bob
    ('Diana',   95000),
    ('Eve',     85000),
    ('Frank',   80000);
SQL — DENSE_RANK (handles ties correctly)
DECLARE @N INT = 3;

WITH Ranked AS (
    SELECT Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS Rnk
    FROM   SalaryTest
)
SELECT DISTINCT Salary
FROM   Ranked
WHERE  Rnk = @N;
-- 1st=120k, 2nd=110k (tie), 3rd=95k → Returns: 95000
SQL — OFFSET/FETCH approach
DECLARE @N INT = 3;

SELECT DISTINCT Salary
FROM   SalaryTest
ORDER BY Salary DESC
OFFSET  (@N - 1) ROWS
FETCH NEXT 1 ROW ONLY;
-- Note: DISTINCT + OFFSET works when DISTINCT reduces before OFFSET
-- For ties, DENSE_RANK approach is more reliable
Using RANK() instead of DENSE_RANK() produces gaps after ties. If two employees share rank 2, RANK() jumps to 4 — there is no rank 3. DENSE_RANK() produces 1, 2, 2, 3 — no gaps.
3

Running Total by Date

SQL — Setup + solution
CREATE TABLE DailySales (
    SaleDate DATE          NOT NULL PRIMARY KEY,
    Amount   DECIMAL(10,2) NOT NULL
);
INSERT INTO DailySales VALUES
    ('2024-01-01',  500.00),
    ('2024-01-02',  750.00),
    ('2024-01-03',  300.00),
    ('2024-01-04', 1200.00),
    ('2024-01-05',  450.00);

SELECT SaleDate,
       Amount,
       SUM(Amount) OVER (
           ORDER BY SaleDate
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningTotal,
       AVG(Amount) OVER (
           ORDER BY SaleDate
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS RunningAvg
FROM   DailySales
ORDER BY SaleDate;

Input

2024-01-01   500.00
2024-01-02   750.00
2024-01-03   300.00
2024-01-04  1200.00
2024-01-05   450.00

Output

01-01   500   500.00   500.00
01-02   750  1250.00   625.00
01-03   300  1550.00   516.67
01-04  1200  2750.00   687.50
01-05   450  3200.00   640.00
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW is explicit and avoids the default RANGE frame which groups ties. When dates are unique, both frames give the same result.

Recursive Employee Hierarchy (Org Chart)

SQL — Full recursive CTE with level + path
CREATE TABLE OrgChart (
    EmployeeID INT          NOT NULL PRIMARY KEY,
    Name       NVARCHAR(100)NOT NULL,
    ManagerID  INT          NULL REFERENCES OrgChart(EmployeeID),
    Title      NVARCHAR(100)NOT NULL
);
INSERT INTO OrgChart VALUES
    (1, 'Sarah Chen', NULL, 'CEO'),
    (2, 'Mark Torres',1,  'VP Engineering'),
    (3, 'Lisa Park',  1,   'VP Marketing'),
    (4, 'James Liu',  2,   'Senior Engineer'),
    (5, 'Ryan Kim',   4,   'Engineer'),
    (6, 'Anna Smith', 3,   'Marketing Manager'),
    (7, 'Zoe Wilson', 6,   'Marketing Coordinator');

WITH OrgHierarchy AS (
    -- Anchor: root employees (no manager)
    SELECT EmployeeID, Name, Title, ManagerID,
           0 AS Level,
           CAST(Name AS NVARCHAR(MAX)) AS OrgPath
    FROM   OrgChart WHERE ManagerID IS NULL

    UNION ALL

    -- Recursive: each direct report, one level deeper
    SELECT e.EmployeeID, e.Name, e.Title, e.ManagerID,
           h.Level + 1,
           h.OrgPath + N' → ' + e.Name
    FROM   OrgChart e
    INNER JOIN OrgHierarchy h ON e.ManagerID = h.EmployeeID
)
SELECT Level,
       REPLICATE(N'    ', Level) + Name AS IndentedName,
       Title, OrgPath
FROM   OrgHierarchy
ORDER BY OrgPath
OPTION (MAXRECURSION 50);

Output (indented)

Level 0  Sarah Chen         CEO
Level 1    Mark Torres      VP Engineering
Level 2      James Liu      Senior Engineer
Level 3        Ryan Kim     Engineer
Level 1    Lisa Park        VP Marketing
Level 2      Anna Smith     Marketing Manager
Level 3        Zoe Wilson   Marketing Coordinator

Find Gaps in a Sequence

SQL — Setup
CREATE TABLE OrderSeq (OrderID INT NOT NULL PRIMARY KEY);
INSERT INTO OrderSeq VALUES
    (1),(2),(3),(5),(6),(9),(10),(11),(15);
-- Missing: 4, 7, 8, 12, 13, 14
SQL — Approach 1: LAG() to find gap boundaries
WITH Gaps AS (
    SELECT OrderID,
           LAG(OrderID) OVER (ORDER BY OrderID) AS PrevID
    FROM   OrderSeq
)
SELECT PrevID + 1    AS GapStart,
       OrderID - 1   AS GapEnd,
       OrderID - PrevID - 1 AS MissingCount
FROM   Gaps
WHERE  OrderID - PrevID > 1;

-- Output:
-- GapStart  GapEnd  MissingCount
--    4         4        1
--    7         8        2
--   12        14        3
SQL — Approach 2: Generate all expected IDs, LEFT JOIN
DECLARE @Min INT = (SELECT MIN(OrderID) FROM OrderSeq);
DECLARE @Max INT = (SELECT MAX(OrderID) FROM OrderSeq);

WITH Numbers AS (
    SELECT @Min AS n
    UNION ALL
    SELECT n + 1 FROM Numbers WHERE n < @Max
)
SELECT n AS MissingID
FROM   Numbers
WHERE  n NOT IN (SELECT OrderID FROM OrderSeq)
OPTION (MAXRECURSION 10000);
-- Output: 4, 7, 8, 12, 13, 14
SQL — Bonus: Find missing dates
WITH DateRange AS (
    SELECT CAST('2024-01-01' AS DATE) AS d
    UNION ALL
    SELECT DATEADD(DAY, 1, d)
    FROM   DateRange
    WHERE  d < '2024-01-31'
)
SELECT d AS MissingDate
FROM   DateRange
WHERE  d NOT IN (SELECT RevenueDate FROM DailyRevenue)
OPTION (MAXRECURSION 400);

Pivot / Cross-Tab — Rows to Columns

SQL — Setup
CREATE TABLE MonthlyCategorySales (
    SaleYear  INT            NOT NULL,
    SaleMonth INT            NOT NULL,
    Category  NVARCHAR(50)  NOT NULL,
    Revenue   DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (SaleYear, SaleMonth, Category)
);
INSERT INTO MonthlyCategorySales VALUES
    (2024,1,'Electronics',50000), (2024,2,'Electronics',62000), (2024,3,'Electronics',58000),
    (2024,1,'Clothing',   30000), (2024,2,'Clothing',   28000), (2024,3,'Clothing',   35000),
    (2024,1,'Books',      12000), (2024,2,'Books',      14000), (2024,3,'Books',      11000);
SQL — CASE WHEN pivot (portable, flexible)
SELECT Category,
       SUM(CASE WHEN SaleMonth = 1 THEN Revenue ELSE 0 END) AS Jan,
       SUM(CASE WHEN SaleMonth = 2 THEN Revenue ELSE 0 END) AS Feb,
       SUM(CASE WHEN SaleMonth = 3 THEN Revenue ELSE 0 END) AS Mar
FROM   MonthlyCategorySales
WHERE  SaleYear = 2024
GROUP BY Category
ORDER BY Category;
SQL — PIVOT operator (SQL Server)
SELECT Category, [1] AS Jan, [2] AS Feb, [3] AS Mar
FROM (
    SELECT Category, SaleMonth, Revenue
    FROM   MonthlyCategorySales WHERE SaleYear = 2024
) AS src
PIVOT (
    SUM(Revenue)
    FOR SaleMonth IN ([1], [2], [3])
) AS pvt
ORDER BY Category;
SQL — Dynamic PIVOT (columns known at runtime)
DECLARE @Cols NVARCHAR(MAX), @SQL NVARCHAR(MAX), @Year INT = 2024;

SELECT @Cols = STRING_AGG(QUOTENAME(SaleMonth), ', ')
FROM (SELECT DISTINCT SaleMonth FROM MonthlyCategorySales WHERE SaleYear = @Year) AS m;

SET @SQL = N'SELECT Category, ' + @Cols + N'
FROM (SELECT Category, SaleMonth, Revenue
      FROM MonthlyCategorySales WHERE SaleYear = ' + CAST(@Year AS NVARCHAR) + N') AS src
PIVOT (SUM(Revenue) FOR SaleMonth IN (' + @Cols + N')) AS pvt ORDER BY Category;';

EXEC sp_executesql @SQL;
-- Always use QUOTENAME() — prevents SQL injection on column names

Input (rows)

Electronics  1  50000
Electronics  2  62000
Clothing     1  30000
Books        2  14000
...

Output (columns)

Books        12000  14000  11000
Clothing     30000  28000  35000

Q: CASE WHEN vs PIVOT — when to use which?

CASE WHEN is portable (works across databases), supports conditions beyond simple aggregation, and is clear to anyone. PIVOT gives cleaner syntax for straightforward pivots in SQL Server. Use Dynamic PIVOT with sp_executesql when columns are unknown at query-write time — always sanitize with QUOTENAME().

Quick Reference Q&A

Q: What happens when you update a clustered index key column?

SQL Server performs a delete + insert (a "row move") because physical ordering must be maintained. All non-clustered indexes that hold the clustering key as a row locator are also updated.
Q: Why can a query be slow even with the right indexes?

Stale statistics (bad cardinality estimates); non-SARGable predicates preventing seeks; implicit type conversions; index fragmentation; parameter sniffing; blocking/lock waits; tempdb spills from hash joins or sorts.
Q: DELETE vs TRUNCATE vs DROP?

DELETE is logged row-by-row, fires triggers, supports WHERE, fully rollback-able. TRUNCATE is minimally logged, removes all rows, resets identity, cannot have WHERE or fire row triggers, rollback-able if inside explicit transaction. DROP removes the table object entirely.
Q: What is a covering index and when to use it?

A covering index includes all columns a query needs (via INCLUDE) so the engine never performs a Key Lookup against the clustered index. Use it when the execution plan shows Key Lookups — add the missing columns to the INCLUDE list of the existing non-clustered index.
Q: What is the difference between RANK and DENSE_RANK?

Both assign the same rank to tied rows. RANK skips the next rank value(s) after a tie — producing gaps. DENSE_RANK never skips — no gaps. For "Nth highest salary" problems, always use DENSE_RANK so ties do not displace lower ranks.
