1. .NET Garbage Collection

How the GC Works

The .NET GC is a generational, tracing garbage collector. It walks object references from GC roots (static fields, stack variables, CPU registers), marks reachable objects, and collects everything else. Objects are promoted through generations based on survival.

Generations

GenerationDescriptionCollection FrequencyTypical Objects
Gen 0Short-lived objectsMost frequent (~every few MB)Local vars, temp buffers
Gen 1Survived one Gen 0 sweepModerateMedium-lived objects
Gen 2Long-lived objectsLeast frequentCaches, static data
LOHObjects >= 85,000 bytesOnly with Gen 2Large arrays, streams
💬 Interview Q — What is the LOH and why does it matter?

"The Large Object Heap stores objects 85KB or larger. Unlike the small object heap, the LOH is not compacted during collection — moving large objects is too expensive. Because LOH collections only happen during Gen 2 GCs, repeated large allocations create Gen 2 pressure and heap fragmentation. In a high-throughput API processing large JSON payloads, this causes measurable latency spikes (GC pause times). The solution: use ArrayPool<byte>.Shared — rent a buffer, use it, return it. Zero new allocations on the hot path."

GC Modes

ModeBest ForThreads
Workstation GCDesktop apps, CLI toolsSingle dedicated GC thread
Server GCWeb servers, microservicesOne GC thread per logical CPU
Background/ConcurrentLow-latency appsGC runs concurrently with app

GC.Collect() — When and When NOT

⚠ Pitfall — Never Call GC.Collect() in Hot Paths

Calling GC.Collect() forces a full collection of ALL generations. The GC is self-tuning — calling it manually disrupts adaptive heuristics and almost always makes performance worse. Only acceptable after a known bulk operation (e.g., loading large startup data).

csharp
// ❌ NEVER — in request handlers or hot paths
public void ProcessRequest()
{
    DoWork();
    GC.Collect(); // Destroys generational heuristics — never do this
}

// ✅ ACCEPTABLE — one-time bulk operation at startup
public void LoadAllReferenceData()
{
    LoadCountries();   // Allocates many temp objects
    LoadCurrencies();
    LoadTimezones();

    // Hint GC after known large allocation burst
    GC.Collect(2, GCCollectionMode.Forced, blocking: true);
    GC.WaitForPendingFinalizers();
}

// ✅ LOH compaction (compact once on next collection)
GCSettings.LargeObjectHeapCompactionMode =
    GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect(); // Resets to Default after this collection

Real Example: Event Handler Memory Leak — Before vs After

❌ Memory Leak — subscriber never freed
public class EventSubscriber
{
    private readonly EventPublisher _publisher;
    // 500KB held per subscriber
    private readonly byte[] _buffer =
        new byte[500_000];

    public EventSubscriber(EventPublisher pub)
    {
        _publisher = pub;
        // ❌ Never unsubscribed
        _publisher.DataReceived +=
            HandleData;
    }

    private void HandleData(object? s,
        DataEventArgs e) { /* ... */ }

    // No Dispose — subscriber can NEVER
    // be GC'd while publisher is alive!
}
✓ Fix — IDisposable + unsubscribe
public class EventSubscriber : IDisposable
{
    private readonly EventPublisher _publisher;
    private readonly byte[] _buffer =
        new byte[500_000];
    private bool _disposed;

    public EventSubscriber(EventPublisher pub)
    {
        _publisher = pub;
        _publisher.DataReceived +=
            HandleData; // ✅ Will be removed
    }

    private void HandleData(object? s,
        DataEventArgs e)
    {
        if (_disposed) return;
        /* process */
    }

    public void Dispose()
    {
        if (_disposed) return;
        // ✅ Remove delegate reference
        _publisher.DataReceived -=
            HandleData;
        _disposed = true;
    }
}

WeakReference<T> — Cache Without Preventing GC

csharp
public class WeakReferenceCache<TKey, TValue> where TValue : class
{
    private readonly Dictionary<TKey, WeakReference<TValue>> _cache = new();

    public TValue? GetOrCreate(TKey key, Func<TKey, TValue> factory)
    {
        if (_cache.TryGetValue(key, out var weakRef) &&
            weakRef.TryGetTarget(out var value))
            return value; // Still alive

        // GC'd or not yet cached — recreate
        value = factory(key);
        _cache[key] = new WeakReference<TValue>(value);
        return value;
    }
}
// If GC needs memory, cached objects CAN be collected — they'll be recreated on demand

3. Object Pooling

💡 When to Use Object Pooling

Use pooling when: frequent allocation of same-sized objects causes LOH pressure, object creation is expensive, high-throughput paths require minimal GC pauses. Classic candidates: byte[] buffers for I/O, StringBuilder instances, DB connections, HttpClient message handlers.

ArrayPool<T> — Before vs After

Zero LOH allocations on hot path Buffer reused across requests
❌ Before — LOH allocation per request
public async Task<byte[]> ProcessRequestBad(
    Stream body)
{
    // ❌ 64KB → Large Object Heap!
    // New allocation on every request
    var buffer = new byte[65536];
    int read = await body.ReadAsync(buffer);
    return buffer[..read].ToArray();
}
✓ After — rent from shared pool
public async Task ProcessRequestGood(
    Stream body, Stream output)
{
    // ✅ Rent from pool — zero new allocation
    byte[] buf =
        ArrayPool<byte>.Shared.Rent(65536);
    try
    {
        int read = await body.ReadAsync(
            buf.AsMemory());
        await output.WriteAsync(
            buf.AsMemory(0, read));
    }
    finally
    {
        // ✅ ALWAYS return in finally
        ArrayPool<byte>.Shared.Return(buf);
    }
}
⚠ Pitfall — Never Use Rented Array After Return

After calling ArrayPool.Return(buffer), another thread may immediately rent that same array. Any access to buffer after return is a concurrency bug. Set the variable to null or let it go out of scope immediately after returning.

ObjectPool<StringBuilder> via DI

csharp
// Program.cs
builder.Services.AddSingleton<ObjectPoolProvider, DefaultObjectPoolProvider>();
builder.Services.AddSingleton(sp =>
{
    var provider = sp.GetRequiredService<ObjectPoolProvider>();
    return provider.Create(new StringBuilderPooledObjectPolicy());
});

public class ReportGenerator
{
    private readonly ObjectPool<StringBuilder> _sbPool;

    public ReportGenerator(ObjectPool<StringBuilder> sbPool) => _sbPool = sbPool;

    public string GenerateReport(IEnumerable<ReportLine> lines)
    {
        var sb = _sbPool.Get(); // Rent (Clear() was called on previous return)
        try
        {
            sb.AppendLine("# Report");
            foreach (var line in lines)
                sb.AppendLine(line.Description);
            return sb.ToString();
        }
        finally
        {
            _sbPool.Return(sb); // Returns to pool — Clear() called automatically
        }
    }
}

public async Task<Product?> GetProductAsync(int id, CancellationToken ct = default)

Distributed Caching — Redis with Cache Stampede Prevention

Cache-aside pattern Double-checked lock prevents stampede
csharp
// Program.cs
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "localhost:6379,abortConnect=false";
    options.InstanceName = "MyApp:";
});

public async Task<Product?> GetProductAsync(int id, CancellationToken ct = default)
{
    string key = $"product:{id}";

    // 1. Fast path — try cache without lock
    var cached = await _cache.GetAsync(key, ct);
    if (cached != null) return Deserialize<Product>(cached);

    // 2. Cache miss — per-key lock prevents stampede
    var keyLock = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await keyLock.WaitAsync(ct);
    try
    {
        // 3. Double-check after lock (another thread may have populated)
        cached = await _cache.GetAsync(key, ct);
        if (cached != null) return Deserialize<Product>(cached);

        // 4. Load from DB
        var product = await _repo.GetByIdAsync(id, ct);
        if (product == null) return null;

        // 5. Store with TTL
        var cacheOpts = new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(2),
            SlidingExpiration = TimeSpan.FromMinutes(20)
        };
        await _cache.SetAsync(key, Serialize(product), cacheOpts, ct);
        return product;
    }
    finally
    {
        keyLock.Release();
        _locks.TryRemove(key, out _);
    }
}

💬 Interview Q — How do you handle cache invalidation?

"Cache invalidation is genuinely hard. My approach uses three layers: 1) TTL as safety net — always set an absolute expiration so data is eventually consistent even if invalidation fails. 2) Event-driven invalidation — when data changes, publish a domain event that removes the specific cache key. For distributed caches, I use Redis pub/sub to broadcast invalidation to all app instances simultaneously. 3) Cache tags for bulk invalidation — Output Cache tags let you evict groups atomically. The main pitfall to avoid: relying solely on TTL for frequently-changing data."

⚠ Pitfall — Never Compress Already-Compressed Formats

Adding image/jpeg, image/png, video/mp4, or application/zip to MIME types wastes CPU and often increases response size by 1-3%. These formats use their own internal compression. Always specify MIME types explicitly — never use a wildcard.

6. Connection Pooling

How ADO.NET Connection Pooling Works

Connection pooling is automatic and transparent in ADO.NET. The pool key is the exact connection string. When you call conn.Open(), ADO.NET reuses an idle physical connection. When you call conn.Dispose(), the physical connection is not closed — it returns to the pool for reuse.

Connection String Parameters
Server=myserver;Database=mydb;User Id=sa;Password=secret;
Min Pool Size=5;              -- Pre-create connections at startup
Max Pool Size=100;            -- Hard cap — requests block at this limit
Connection Timeout=30;        -- Wait timeout for pooled connection
Connect Timeout=15;           -- Timeout for new physical connection
Pooling=true;                 -- Default: true

Connection Leak — Before vs After

❌ Leak — pool exhausted after 100 requests
public async Task<List<Product>> GetProductsLeaky()
{
    // ❌ Never disposed
    var conn = new SqlConnection(_cs);
    await conn.OpenAsync();

    var cmd = new SqlCommand(
        "SELECT * FROM Products", conn);
    var reader =
        await cmd.ExecuteReaderAsync();

    var list = new List<Product>();
    while (await reader.ReadAsync())
        list.Add(Map(reader));
    return list;
    // ❌ conn never Dispose()d
    // Pool exhausts → SqlException on
    // new requests
}
✓ Fix — await using returns to pool
public async Task<List<Product>> GetProductsGood()
{
    // ✅ await using — always Dispose()
    await using var conn =
        new SqlConnection(_cs);
    await conn.OpenAsync();

    await using var cmd = new SqlCommand(
        "SELECT Id, Name FROM Products WHERE IsActive=1", conn);
    await using var reader =
        await cmd.ExecuteReaderAsync();

    var list = new List<Product>();
    while (await reader.ReadAsync())
        list.Add(Map(reader));
    return list;
} // ✅ conn.Dispose() → back to pool
💡 Tip — Size Your Pool to Peak Concurrency

For an API handling 500 concurrent requests each holding a connection for 100ms, you need ~50 connections. Set Max Pool Size to ~2× expected peak to absorb traffic spikes. Monitor sys.dm_exec_connections in SQL Server to see actual usage.

8. Async Performance

ValueTask vs Task — Zero-Allocation Hot Paths

Zero allocation on synchronous path Don't await ValueTask more than once
❌ Task — always allocates
// ❌ Always allocates Task object
public async Task<Product?> GetProductAsync(int id)
{
    return await _db.Products.FindAsync(id);
}
// Even on cache hit: Task allocated
✓ ValueTask — zero alloc on sync path
// ✅ Struct on stack when cache hits
public ValueTask<Product?> GetProductAsync(int id)
{
    if (_cache.TryGetValue(id, out var p))
        return ValueTask.FromResult(p); // ✅ No alloc

    return new ValueTask<Product?>(
        FetchFromDbAsync(id)); // Async path
}

Thread Pool Starvation — The Deadlock Pattern

❌ Sync-over-async — blocks threads
[HttpGet("data")]
public IActionResult GetData()
{
    // ❌ .Result blocks thread pool thread
    // Under load: all threads blocked,
    // new requests starve
    var result = _service
        .GetDataAsync().Result;
    return Ok(result);
}
✓ Async all the way
[HttpGet("data")]
public async Task<IActionResult> GetData()
{
    // ✅ Thread released while awaiting
    // Thread pool thread serves other
    // requests while I/O completes
    var result = await _service.GetDataAsync();
    return Ok(result);
}

CPU-Bound vs I/O-Bound

csharp
// I/O-bound — async/await directly (no Task.Run)

💬 Interview Q — How do you detect thread pool starvation?

"I use dotnet-counters to monitor threadpool-thread-count and threadpool-queue-length in real time. Starvation shows as: thread count growing steadily, queue length growing, request latency increasing. Root cause is almost always sync-over-async (.Result or .Wait()) in a high-concurrency path. Fix: make the entire call chain async. Never mix blocking calls with async code."

9. BenchmarkDotNet

BenchmarkDotNet is the standard for .NET micro-benchmarking. It handles JIT warmup, statistical analysis, outlier detection, and memory diagnostics automatically. Always run in Release mode.

csharp — Full String Benchmark
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
[SimpleJob(RuntimeMoniker.Net80)]
[RankColumn]
[Orderer(SummaryOrderPolicy.FastestToSlowest)]
public class StringConcatBenchmarks

    private string[] _words = null!;

    [GlobalSetup] // Runs ONCE before all benchmark iterations
    public void Setup()
    {
        _words = Enumerable.Range(0, Iterations)
            .Select(i => $"word{i:D4}")
            .ToArray();
    }

    [Benchmark(Baseline = true)]
    public string PlusOperator()
    {
        string result = "";
        foreach (var word in _words) result += word;
        return result;
    }

    [Benchmark]
    public string StringBuilderPreSized()
    {
        var sb = new StringBuilder(Iterations * 8);
        foreach (var word in _words) sb.Append(word);
        return sb.ToString();
    }

    [Benchmark]
    public string StringConcat() => string.Concat(_words);

    [Benchmark]
    public string StringCreate()
    {
        int len = _words.Sum(w => w.Length);
        return string.Create(len, _words, (span, words) =>
        {
            int pos = 0;
            foreach (var w in words)
            {
                w.AsSpan().CopyTo(span[pos..]);
                pos += w.Length;
            }
        });
    }
}

10. String Performance

Span<char> — Zero-Allocation CSV Parsing

❌ Split — 3+ allocations per line
public static (int, string, decimal) ParseBad(string line)
{
    // ❌ Allocates: string[], each field
    var parts = line.Split(',');
    return (
        int.Parse(parts[0]),
        parts[1],           // new string
        decimal.Parse(parts[2])
    );
}
✓ Span — zero heap allocations
public static (int, ReadOnlySpan<char>, decimal)
    ParseGood(ReadOnlySpan<char> line)
{
    int c1 = line.IndexOf(',');
    int c2 = line[(c1+1)..].IndexOf(',')+c1+1;
    return (
        int.Parse(line[..c1]),    // ✅ No alloc
        line[(c1+1)..c2],         // ✅ Slice
        decimal.Parse(line[(c2+1)..]) // ✅ No alloc
    );
}

⚠ Warning — String Interning Pitfall

Never call string.Intern(userInput) on user-supplied strings. Interned strings live for the entire app lifetime and cannot be GC'd. An attacker could exhaust memory by submitting unique strings. Only intern known, bounded sets of strings (e.g., XML element names, enum labels).

12. HTTP Client Performance

⚠ Pitfall — Why new HttpClient() Per Request Causes Port Exhaustion

When you Dispose() an HttpClient, the underlying socket enters TIME_WAIT state at the OS level (~240 seconds). At 100 requests/sec × 240 seconds = 24,000 ports exhausted. Result: SocketException: address already in use. IHttpClientFactory solves this by pooling HttpMessageHandler instances and rotating them every 2 minutes to respect DNS changes.

Typed Client — Preferred Pattern

❌ New client per request
public async Task<string> GetDataBad(string url)
{
    // ❌ New socket per request
    // ❌ Socket enters TIME_WAIT on dispose
    // ❌ Port exhaustion under load
    using var client = new HttpClient();
    return await client.GetStringAsync(url);
}
✓ Typed client via IHttpClientFactory
// ✅ Program.cs
builder.Services.AddHttpClient<IGitHubClient, GitHubClient>(client =>
{
    client.BaseAddress = new Uri("https://api.github.com");
    client.Timeout = TimeSpan.FromSeconds(30);
}).SetHandlerLifetime(TimeSpan.FromMinutes(5));

// ✅ Typed client — HttpClient injected, shared
public class GitHubClient : IGitHubClient
{
    private readonly HttpClient _client;
    public GitHubClient(HttpClient c) => _client = c;

    public Task<GitHubRepo?> GetRepoAsync(string o, string r) =>
        _client.GetFromJsonAsync<GitHubRepo>($"/repos/{o}/{r}");
}

// Retry: 3 attempts with exponential backoff (1s, 2s, 4s)
// Circuit breaker: opens after 50% failures over 30s, min 10 requests
// Total timeout: abort request after 10s regardless of retry state
💬 Interview Q — Why does new HttpClient() per request cause problems?

"HttpClient internally uses HttpMessageHandler which owns socket connections. When you Dispose() an HttpClient, the underlying socket doesn't immediately close — it enters TIME_WAIT at the OS level for ~240 seconds. Creating 100 HttpClient instances per second exhausts available ports (~65,535 total). IHttpClientFactory solves this by maintaining a pool of HttpMessageHandler instances — they're shared across requests. It also rotates handlers every 2 minutes (configurable) to respect DNS TTL changes, which matters for Kubernetes services and AWS Route 53."
