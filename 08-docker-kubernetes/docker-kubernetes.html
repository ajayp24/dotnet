1. Dockerfile Best Practices

Why Layer Order Matters

Docker builds images as a stack of layers. When a layer changes, all subsequent layers are invalidated and rebuilt. The golden rule: put things that change least at the top.

Layer order — slowest to rebuild at top, fastest at bottom: FROM base-image <─ almost never changes RUN install packages <─ changes rarely COPY project files <─ changes when dependencies change RUN dotnet restore <─ cached when project files unchanged COPY source code <─ changes on every commit RUN dotnet publish <─ always rebuilds after code changes

Best Practice Checklist

PracticeReason
COPY .csproj files before sourceNuGet restore is cached until dependencies change
Multi-stage buildDiscard SDK / build tools from final image (800MB → 200MB)
.dockerignorePrevent sending bin/, obj/, .git/ to Docker daemon
Non-root userReduce blast radius if container is compromised
HEALTHCHECK instructionDocker can automatically restart unhealthy containers
Pin image tagsaspnet:8.0 not aspnet:latest — reproducible builds
Exec form ENTRYPOINTSIGTERM goes directly to .NET process, not shell wrapper

Before vs After — Naive vs Optimized

BEFORE — Naive (do not use)
# Rebuilds everything on every code change
# Ships 800MB SDK to production
# Runs as root
FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /app
COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /out
ENTRYPOINT ["dotnet", "/out/MyApi.dll"]
AFTER — Optimized (use this)
# Multi-stage, non-root, health check
# Ships ~200MB runtime image
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY ["MyApi.csproj", "."]
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
RUN adduser --system --group appuser
WORKDIR /app
COPY --from=build /app .
HEALTHCHECK --interval=30s --timeout=10s \
  CMD curl -f http://localhost:8080/health || exit 1
USER appuser
ENTRYPOINT ["dotnet", "MyApi.dll"]

Complete .NET 8 Web API Multi-stage Dockerfile

Dockerfile
# ─────────────────────────────────────────────────────────────────────────────
# Multi-stage Dockerfile for .NET 8 Web API
# Build:  docker build -t myapi:latest .
# Run:    docker run -p 8080:8080 myapi:latest
# ─────────────────────────────────────────────────────────────────────────────

ARG DOTNET_VERSION=8.0

# ── Stage 1: Restore ────────────────────────────────────────────────────────
FROM mcr.microsoft.com/dotnet/sdk:${DOTNET_VERSION} AS restore
WORKDIR /src

# Copy solution + project files FIRST for dependency caching
COPY ["MyApi.sln", "."]
COPY ["src/MyApi/MyApi.csproj",                         "src/MyApi/"]
COPY ["src/MyApi.Application/MyApi.Application.csproj", "src/MyApi.Application/"]
COPY ["src/MyApi.Domain/MyApi.Domain.csproj",           "src/MyApi.Domain/"]
COPY ["src/MyApi.Infrastructure/MyApi.Infrastructure.csproj", "src/MyApi.Infrastructure/"]
COPY ["tests/MyApi.Tests/MyApi.Tests.csproj",           "tests/MyApi.Tests/"]

# This layer is cached until any .csproj changes
RUN dotnet restore "MyApi.sln"

# ── Stage 2: Build ──────────────────────────────────────────────────────────
FROM restore AS build
COPY . .
RUN dotnet build "MyApi.sln" -c Release --no-restore

# ── Stage 3: Test (skip with --target publish in CI) ────────────────────────
FROM build AS test
RUN dotnet test "tests/MyApi.Tests/MyApi.Tests.csproj" \
    -c Release --no-build \
    --logger "trx;LogFileName=results.trx" \
    --results-directory /TestResults

# ── Stage 4: Publish ────────────────────────────────────────────────────────
FROM build AS publish
RUN dotnet publish "src/MyApi/MyApi.csproj" \
    -c Release --no-build \
    --runtime linux-x64 \
    --self-contained false \
    -o /app/publish \
    /p:UseAppHost=false

# ── Stage 5: Final Runtime Image ────────────────────────────────────────────
FROM mcr.microsoft.com/dotnet/aspnet:${DOTNET_VERSION} AS final
WORKDIR /app

# Non-root user for security
RUN groupadd --system appgroup \
    && useradd --system --gid appgroup --no-create-home appuser

COPY --from=publish --chown=appuser:appgroup /app/publish .

ENV ASPNETCORE_URLS=http://+:8080 \
    ASPNETCORE_ENVIRONMENT=Production \
    DOTNET_RUNNING_IN_CONTAINER=true

HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
    CMD curl -f http://localhost:8080/health/live || exit 1

USER appuser
EXPOSE 8080
ENTRYPOINT ["dotnet", "MyApi.dll"]
💡
Interview tip — exec vs shell form
Use exec form ENTRYPOINT ["dotnet", "MyApi.dll"] not shell form ENTRYPOINT dotnet MyApi.dll. Shell form wraps in /bin/sh -c, so SIGTERM goes to the shell, not your .NET process. Graceful shutdown requires exec form.

3. Image Layers and Caching

Cache Invalidation Rules

Layer invalidation example
# Layer 1 — cached as long as base image hash is unchanged
FROM mcr.microsoft.com/dotnet/sdk:8.0

# Layer 2 — cached as long as command string is identical
RUN apt-get update && apt-get install -y curl

# Layer 3 — INVALIDATED when any .csproj file changes
COPY **/*.csproj ./

# Layer 4 — INVALIDATED when layer 3 is invalidated (re-runs dotnet restore)
RUN dotnet restore

# Layer 5 — INVALIDATED on every source code change
COPY . .

# Layer 6 — always invalidated after layer 5
RUN dotnet publish -c Release -o /out

Inspecting Layer Sizes

bash
# Show all layers with sizes
docker history myapi:latest

# Detailed JSON output of layer info
docker inspect myapi:latest | jq '.[0].RootFS.Layers'

# Compare image sizes
docker images myapp/api --format "table {{.Repository}}\t{{.Tag}}\t{{.Size}}"
⚠️
Pitfall — Alpine and globalization
Alpine uses musl libc. .NET globalization features (ICU data, timezone handling) may behave unexpectedly. Add ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1 for simple apps, or use Debian-based images for full globalization support.

Secret — Sensitive Values

⚠️
Secrets are NOT encrypted by default
Kubernetes Secrets are base64-encoded, not encrypted. Anyone with RBAC access can decode them with kubectl get secret myapi-secrets -o jsonpath='{.data.password}' | base64 -d. Use External Secrets Operator + AWS Secrets Manager / Azure Key Vault for real security.
secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapi-secrets
  namespace: production
type: Opaque
stringData:
  # stringData: Kubernetes base64-encodes these automatically
  ConnectionStrings__SqlServer: "Server=sqlserver;Database=MyDb;User Id=sa;Password=secret;"
  ConnectionStrings__Redis: "redis:6379,password=redispassword"
  Jwt__Secret: "super-secret-jwt-key-minimum-32-chars!!"

Injecting into Pods

env injection patterns
containers:
  - name: myapi

    # Option 1: All keys from ConfigMap as env vars
    envFrom:
      - configMapRef:
          name: myapi-config
      - secretRef:
          name: myapi-secrets

    # Option 2: Individual keys
    env:
      - name: ConnectionStrings__SqlServer
        valueFrom:
          secretKeyRef:
            name: myapi-secrets
            key: ConnectionStrings__SqlServer
      - name: POD_NAME
        valueFrom:
          fieldRef:
            fieldPath: metadata.name

    # Option 3: Mounted as files
    volumeMounts:
      - name: config-volume
        mountPath: /app/config
        readOnly: true

volumes:
  - name: config-volume
    configMap:
      name: myapi-config
      items:
        - key: appsettings.override.json
          path: appsettings.override.json

8. Liveness and Readiness Probes

ProbeAction on FailurePurpose
StartupRestart if never succeedsGive slow-starting apps time to init
LivenessRestart the containerDetect deadlock / hung process
ReadinessRemove from Service endpointsDependency check; only route to healthy pods

ASP.NET Core Health Check Endpoints

Program.cs
// Register health checks
builder.Services.AddHealthChecks()
    .AddSqlServer(
        connectionString: builder.Configuration.GetConnectionString("SqlServer")!,
        name: "database",
        tags: ["ready"])
    .AddRedis(
        redisConnectionString: builder.Configuration.GetConnectionString("Redis")!,
        name: "redis",
        tags: ["ready"])
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);

// Map endpoints
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
probe configuration
containers:
  - name: myapi
    image: myapp/api:1.3.0

    # Startup probe — handles slow initialization (up to 5 minutes)
    startupProbe:
      httpGet:
        path: /health/live
        port: 8080
      failureThreshold: 30      # 30 × 10s = 5 minutes max startup time
      periodSeconds: 10

    # Liveness — restart if deadlocked
    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      periodSeconds: 15
      timeoutSeconds: 5
      failureThreshold: 3

    # Readiness — only route traffic when DB + Redis are reachable
    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 5
      failureThreshold: 3
      successThreshold: 1
⚠️
Pitfall — liveness probe too aggressive
Setting initialDelaySeconds too low on liveness probes kills pods still warming up. Use startupProbe for slow-starting apps instead. Once startup probe succeeds, liveness and readiness probes take over.

9. HPA — Horizontal Pod Autoscaler

hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapi-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapi-deployment

  minReplicas: 2
  maxReplicas: 20

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 100          # Double pods at most
          periodSeconds: 60
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300  # 5 min cooldown
      policies:
        - type: Percent
          value: 25           # Remove 25% per period
          periodSeconds: 60
      selectPolicy: Min

10. Rolling Updates and Rollback

Rolling update — maxSurge=1, maxUnavailable=0, replicas=4: Before: [v1] [v1] [v1] [v1] Step 1: [v1] [v1] [v1] [v1] [v2] ← v2 added (5 total) Step 2: [v1] [v1] [v1] [v2] ← one v1 removed Step 3: [v1] [v1] [v2] [v2] Step 4: [v1] [v2] [v2] [v2] After: [v2] [v2] [v2] [v2] ← complete, no downtime
kubectl rollout commands
# Deploy new image version
kubectl set image deployment/myapi-deployment myapi=myapp/api:1.3.0 -n production

# Watch progress
kubectl rollout status deployment/myapi-deployment -n production

# View history
kubectl rollout history deployment/myapi-deployment -n production

# View specific revision details
kubectl rollout history deployment/myapi-deployment --revision=3 -n production

# Rollback to previous version
kubectl rollout undo deployment/myapi-deployment -n production

# Rollback to specific revision
kubectl rollout undo deployment/myapi-deployment --to-revision=2 -n production

# Pause mid-rollout (investigate an issue)
kubectl rollout pause deployment/myapi-deployment -n production

# Resume
kubectl rollout resume deployment/myapi-deployment -n production

Blue/Green Deployment

blue-green.yaml
# Blue Deployment — currently live
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapi-blue
spec:
  replicas: 4
  selector:
    matchLabels: { app: myapi, version: blue }
  template:
    metadata:
      labels: { app: myapi, version: blue }
    spec:
      containers:
        - name: myapi
          image: myapp/api:1.2.0
---
# Green Deployment — new version (not live yet)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapi-green
spec:
  replicas: 4
  selector:
    matchLabels: { app: myapi, version: green }
  template:
    metadata:
      labels: { app: myapi, version: green }
    spec:
      containers:
        - name: myapi
          image: myapp/api:1.3.0
---
# Service — switch traffic by changing selector
apiVersion: v1
kind: Service
metadata:
  name: myapi-service
spec:
  selector:
    app: myapi
    version: blue      # Change to "green" to switch instantly
  ports:
    - port: 80
      targetPort: 8080
Switch traffic atomically
# Switch all traffic to green (atomic, instant)
kubectl patch service myapi-service -n production \
  -p '{"spec":{"selector":{"version":"green"}}}'

# Rollback instantly if issues found
kubectl patch service myapi-service -n production \
  -p '{"spec":{"selector":{"version":"blue"}}}'

11. Resource Requests and Limits

SettingPurposeBehavior when exceeded
requests.cpuScheduler minimum — guaranteed CPUPod scheduled only on nodes with this capacity
limits.cpuMaximum CPUThrottled (slowed), NOT killed
requests.memoryScheduler minimum — guaranteed memoryPod scheduled only on nodes with this capacity
limits.memoryMaximum memoryOOMKilled (exit code 137)

QoS Classes

QoS ClassConditionEviction Priority
Guaranteedrequests == limits for all resourcesLast to be evicted
BurstableSome resources have requests < limitsEvicted after BestEffort
BestEffortNo requests or limits setFirst to be evicted
resource configuration + OOMKilled fix
# ── Guaranteed QoS (requests == limits) ────────────────────────────────────
resources:
  requests:
    cpu: "500m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

# ── Burstable QoS (limits > requests) ──────────────────────────────────────
resources:
  requests:
    cpu: "250m"
    memory: "128Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"

# ── .NET GC tuning to prevent OOMKilled ────────────────────────────────────
env:
  - name: DOTNET_GCConserveMemory
    value: "5"                  # 0-9, higher = more conservative GC
  - name: DOTNET_GCHeapHardLimitPercent
    value: "75"               # Use 75% of container limit as hard cap
Diagnose OOMKilled
# Check if a pod was OOMKilled
kubectl describe pod myapi-pod-xyz -n production
# Look for: Reason: OOMKilled / Exit Code: 137

# Check events for OOM
kubectl get events -n production --sort-by=.lastTimestamp | grep -i oom

# Check live memory usage
kubectl top pods -n production

# Check memory usage over time (requires metrics-server)
kubectl top pods -n production --sort-by=memory

12. Kubernetes Networking

DNS Resolution

DNS format: <service-name>.<namespace>.svc.cluster.local Examples (from any pod in the cluster): myapi-service.production.svc.cluster.local → 10.96.45.123 postgres.production.svc.cluster.local → 10.96.45.124 redis.production.svc.cluster.local → 10.96.45.125 Short form (within same namespace): myapi-service → resolves automatically postgres → resolves automatically Cross-namespace short form: myapi-service.production → resolves from other namespaces

NetworkPolicy — Allow Only Frontend to Backend

networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  # Apply this policy to backend pods
  podSelector:
    matchLabels:
      app: myapi
      tier: backend

  policyTypes:
    - Ingress
    - Egress

  ingress:
    # Allow traffic FROM frontend pods only
    - from:
        - podSelector:
            matchLabels:
              app: frontend
              tier: web
      ports:
        - protocol: TCP
          port: 8080

    # Allow Prometheus scraping from monitoring namespace
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: monitoring
          podSelector:
            matchLabels:
              app: prometheus
      ports:
        - protocol: TCP
          port: 9090

  egress:
    # Allow to SQL Server

Interview Q&A

What is the difference between a liveness and readiness probe?
Liveness answers "is the container alive?" — failure restarts the container. Use it to detect deadlocks or hung processes.

Readiness answers "is the container ready to receive traffic?" — failure removes the pod from the Service endpoint list but does not restart it. Use it to check dependencies (database reachability, cache connectivity) and to drain during overload.

Startup probe handles slow-starting apps. It runs first; once it passes, liveness and readiness take over. Without it, liveness probes would kill a legitimate app that simply needs time to initialize.
How do you achieve zero-downtime deployments in Kubernetes?
Set maxUnavailable: 0 so pods never drop below desired count. Set maxSurge: 1 so new pods are added before old ones terminate. Configure readiness probes so traffic only routes to healthy pods. Add a preStop lifecycle hook with a brief sleep (5-10s) to allow the load balancer time to drain existing connections. Ensure terminationGracePeriodSeconds is long enough for in-flight requests to complete.
What is OOMKilled and how do you fix it?
OOMKilled (exit code 137) means the container exceeded its memory limits and was killed by the Linux OOM killer. Fix options: (1) increase the memory limit, (2) find and fix a memory leak using dotnet-monitor or heap dumps, (3) tune .NET GC with DOTNET_GCHeapHardLimitPercent=75 to prevent GC from growing past 75% of the container limit, (4) add HPA to spread load so individual pods use less memory.
How is a Kubernetes Secret different from a ConfigMap? How do you secure secrets properly?
ConfigMap stores plain-text non-sensitive configuration. Secret stores base64-encoded data — but base64 is encoding, not encryption. Anyone with RBAC read access to Secrets can decode them.

For real security: use External Secrets Operator to sync secrets from AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault into Kubernetes Secrets. The plaintext never lives in etcd. Also enable etcd encryption at rest at the cluster level, restrict Secret RBAC with least-privilege roles, and avoid printing secrets in logs.
Explain QoS classes and when each is appropriate.
Guaranteed (requests == limits): Pod is never evicted under memory pressure unless the node itself fails. Use for latency-sensitive APIs and stateful workloads.

Burstable (requests < limits): Pod can use more than requested when capacity is available, but may be evicted under node pressure. Suitable for most services that benefit from bursty capacity.

BestEffort (no resources defined): First to be evicted under pressure. Never use for production workloads. Acceptable only for non-critical batch jobs that can tolerate interruption.
How does Docker layer caching work and how do you optimize it?
Each Dockerfile instruction creates a layer identified by a hash of the instruction and its inputs. When a layer's hash changes, all subsequent layers are invalidated and rebuilt.

Optimize by ordering from most stable to most volatile: base image → OS packages → project/dependency files → dotnet restore → source code → build. Copy only .csproj files first and run restore — this layer is cached until dependencies change. Copy source code after, so code changes only invalidate the final build steps, not the slow restore.
What is the difference between CPU requests/limits and memory requests/limits?
CPU is a compressible resource: if a container exceeds its limit, the kernel throttles it (the container slows down but keeps running). Memory is incompressible: if a container exceeds its limit, the Linux OOM killer terminates it (exit code 137, OOMKilled).

Requests are used by the scheduler to decide which node to place the pod on — the pod is guaranteed at least this amount. Limits are runtime enforcement — the maximum the container can consume.
Blue/Green vs Canary vs Rolling — when do you use each?
Rolling: gradual replacement of old pods with new ones. Low risk, no extra infrastructure. Default for most deployments.

Blue/Green: two identical environments, instant traffic switch via Service selector update. Enables instant rollback. Requires 2x compute. Use when you need atomic cutover and instant rollback (e.g., schema migrations that are backward-incompatible only if you switch back slowly).

Canary: small percentage of traffic to new version. Validate with real traffic before full rollout. Use when you want data-driven confidence (error rates, latency) before committing. Requires Ingress weight support (NGINX canary annotations, Argo Rollouts, or Istio traffic splitting).
