1Middleware Pipeline

Every HTTP request in ASP.NET Core flows through a pipeline of middleware components. Each component can inspect, modify, short-circuit, or pass the request to the next component. The pipeline is bidirectional — code runs both on the way in (request) and on the way out (response).

Use, Run, Map, MapWhen

csharp 
// Use — calls next middleware (bidirectional)
app.Use(async (context, next) =>
{
    Console.WriteLine("→ Before");
    await next(context);          // pass to next component
    Console.WriteLine("← After");  // runs on the way back out
});

// Run — terminal, never calls next
app.Run(async context =>
    await context.Response.WriteAsync("Short-circuit!"));

// Map — branches pipeline on URL prefix
app.Map("/admin", admin =>
    admin.Run(async ctx =>
        await ctx.Response.WriteAsync("Admin area")));

// MapWhen — branches on any condition
app.MapWhen(
    ctx => ctx.Request.Query.ContainsKey("debug"),
    debug => debug.Run(async ctx =>
        await ctx.Response.WriteAsync("Debug mode on")));

// UseWhen — branches but REJOINS the main pipeline
app.UseWhen(
    ctx => ctx.Request.Path.StartsWithSegments("/api"),
    apiApp => apiApp.UseMiddleware<ApiKeyMiddleware>());

Custom Middleware Class

csharp 
public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(RequestDelegate next,
        ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            await _next(context);
        }
        finally
        {
            sw.Stop();
            _logger.LogInformation(
                "{Method} {Path} → {Status} in {Ms}ms",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                sw.ElapsedMilliseconds);
        }
    }
}

// Extension method — clean registration
public static class MiddlewareExtensions
{
    public static IApplicationBuilder UseRequestTiming(
        this IApplicationBuilder app)
        => app.UseMiddleware<RequestTimingMiddleware>();
}

Correct Middleware Order in Program.cs

Order is critical. Wrong order = silent security bugs or broken behaviour.

1app.UseExceptionHandler() — catch all unhandled exceptions first
2app.UseHsts() — HTTPS security header
3app.UseHttpsRedirection() — upgrade HTTP → HTTPS
4app.UseStaticFiles() — serve files without hitting routing
5app.UseRouting() — match URL to endpoint
6app.UseCors() — must be after routing, before auth
7app.UseAuthentication() — who are you?
8app.UseAuthorization() — what can you do?
9app.UseRequestTiming() — custom middleware
10app.MapControllers() — execute matched endpoint
Interview Question

Q: Explain the request pipeline in ASP.NET Core. What happens when a request comes in?

A: Each request enters the pipeline and passes sequentially through middleware components. Each component runs code before calling next() (request phase), then runs more code after next() returns (response phase). Run terminates the pipeline. Map branches on URL prefix. The pipeline is configured in Program.cs using WebApplicationBuilder and order matters — authentication must run before authorization, routing before CORS, etc.

Interview Question

Q: What is the difference between Use, Run, and Map?

A: Use — calls next, bidirectional (runs on both request and response pass). Run — terminal, never calls next, short-circuits the pipeline. Map — branches the pipeline for a URL prefix, the branch does not rejoin. UseWhen — like Map but the branch rejoins after. MapWhen — like Map but branches on a predicate instead of a path.

Pitfall

UseAuthorization before UseAuthentication — authorization runs but the user principal is never populated, so all [Authorize] checks silently fail or throw. Always: Authentication then Authorization.

Pitfall

UseStaticFiles after UseRouting — static files bypass routing entirely; placing them after UseRouting means the routing middleware wastes cycles on every .js/.css request. Put UseStaticFiles early.

Captive Dependency — Classic Bug

csharp — THE BUG 
// Singleton captures a Scoped service — CAPTIVE DEPENDENCY!
builder.Services.AddSingleton<IReportService, ReportService>();
builder.Services.AddScoped<IDbContext, AppDbContext>();

public class ReportService  // singleton...
{
    private readonly IDbContext _db;  // ...holds scoped service = BUG

    public ReportService(IDbContext db)
        => _db = db;  // same DbContext for ALL requests forever!
}

// Runtime: InvalidOperationException in development
// (scope validation is off in production by default — silent data corruption)
csharp — THE FIX 
public class ReportService  // singleton
{
    private readonly IServiceScopeFactory _scopeFactory;

    public ReportService(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;  // IServiceScopeFactory is always singleton-safe

    public async Task<Report> GenerateAsync(Guid id)
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<IDbContext>();
        // db is properly scoped — disposed when the using block exits
        return await db.Reports.FindAsync(id);
    }
}

Interview Question

Q: What happens if a Singleton service depends on a Scoped service?

A: This is the captive dependency problem. The Singleton is created once and holds a reference to the Scoped service forever. That Scoped instance (e.g., DbContext) leaks across all subsequent HTTP requests, causing data corruption, connection exhaustion, and concurrency bugs. In development ASP.NET Core throws InvalidOperationException (scope validation is enabled). Fix: inject IServiceScopeFactory and create a scope per operation.

Tip

Enable scope validation in production too: builder.Host.UseDefaultServiceProvider(o => o.ValidateScopes = true). The performance cost is negligible and it catches captive dependencies before they cause data bugs.

Endpoint Filters (equivalent of Action Filters)

csharp 
public class ValidationFilter<T> : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var arg = context.Arguments.OfType<T>().FirstOrDefault();
        if (arg is null) return Results.BadRequest("Missing body");

        var errors = new List<ValidationResult>();
        if (!Validator.TryValidateObject(arg,
            new ValidationContext(arg), errors, validateAllProperties: true))
        {
            return Results.ValidationProblem(
                errors.ToDictionary(
                    e => e.MemberNames.FirstOrDefault() ?? "error",
                    e => new[] { e.ErrorMessage ?? "Invalid" }));
        }
        return await next(context);
    }
}

Interview Question

Q: When would you choose Minimal APIs over MVC Controllers?

A: Minimal APIs for microservices, API-only projects, high-throughput scenarios (less reflection overhead), and when simplicity is valued. MVC Controllers for large apps requiring complex model binding, Views, Areas, the full filter pipeline with global attributes, or when the team is more familiar with traditional MVC patterns. Both support DI, middleware, OpenAPI, and authentication equally well.

4MVC

csharp — Controller with typed results 
[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orders;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(IOrderService orders, ILogger<OrdersController> logger)
        => (_orders, _logger) = (orders, logger);

    [HttpGet("{id:guid}")]
    [ProducesResponseType<OrderDto>(StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public async Task<ActionResult<OrderDto>> GetOrder(Guid id)
    {
        var order = await _orders.GetAsync(id);
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    [ProducesResponseType<OrderDto>(StatusCodes.Status201Created)]
    [ProducesResponseType<ValidationProblemDetails>(StatusCodes.Status400BadRequest)]
    public async Task<ActionResult<OrderDto>> CreateOrder(
        [FromBody] CreateOrderRequest request)
    {
        // [ApiController] auto-validates and returns 400 if invalid
        // No need for: if (!ModelState.IsValid) return BadRequest();
        var order = await _orders.CreateAsync(request);
        return CreatedAtAction(nameof(GetOrder), new { id = order.Id }, order);
    }
}

csharp 
public class CreateOrderValidator : AbstractValidator<CreateOrderRequest>
{
    public CreateOrderValidator(IProductRepository products)
    {
        RuleFor(x => x.CustomerEmail)
            .NotEmpty()
            .EmailAddress()
            .MaximumLength(254);

        RuleFor(x => x.Items)
            .NotEmpty().WithMessage("Order must have at least one item")
            .Must(items => items.All(i => i.Quantity > 0))
            .WithMessage("All quantities must be positive");

        RuleForEach(x => x.Items).ChildRules(item =>

                .MustAsync(async (id, ct) => await products.ExistsAsync(id, ct))
                .WithMessage("Product not found"));
    }
}

Interview Question

Q: What is model binding source order in ASP.NET Core?

A: Without attributes, MVC tries sources in order: Form fields → Route data → Query string. Attributes override: [FromBody] (JSON/XML body), [FromRoute], [FromQuery], [FromHeader], [FromForm], [FromServices]. With [ApiController], complex types default to [FromBody] automatically.

Pitfall

Manually checking ModelState.IsValid in an [ApiController] controller is redundant — the attribute triggers automatic 400 responses before your action runs. Remove the check; it only adds noise.

[Route("api/v{version:apiVersion}/products")]

Interview Question

Q: How do you version a REST API without breaking existing clients?

A: Keep the old version running, introduce a new URL segment (/v2/), mark the old one Deprecated = true (the framework adds api-deprecated-versions headers so clients can detect it). Clients on v1 continue working unchanged. Once deprecation period ends and usage metrics show zero v1 traffic, remove the old controller. Never change the contract of an existing version.

Pitfall

Not setting AssumeDefaultVersionWhenUnspecified = true means existing clients without a version in their URL or headers will receive 400 Bad Request: API version is not specified the moment you add versioning middleware.

csharp — Exception Filter with pattern matching 
public class GlobalExceptionFilter : IExceptionFilter
{
    private readonly ILogger<GlobalExceptionFilter> _logger;
    public GlobalExceptionFilter(ILogger<GlobalExceptionFilter> logger)
        => _logger = logger;

    public void OnException(ExceptionContext context)
    {
        _logger.LogError(context.Exception, "Unhandled: {Action}",
            context.ActionDescriptor.DisplayName);

        var (status, title) = context.Exception switch
        {
            NotFoundException e  => (404, e.Message),
            ValidationException e => (422, e.Message),
            UnauthorizedAccessException => (403, "Access denied"),
            ConflictException e   => (409, e.Message),
            _                      => (500, "An unexpected error occurred")
        };

        context.Result = new ObjectResult(new ProblemDetails
        {
            Status   = status,
            Title    = title,
            Instance = context.HttpContext.Request.Path
        }) { StatusCode = status };

        context.ExceptionHandled = true;
    }
}

Interview Question

Q: What is the execution order of filters, and how do you control it?

A: Authorization → Resource → (Model Binding) → Action (before) → Action executes → Action (after) → Exception → Result (before) → Result renders → Result (after). Control order via the Order property on the filter (lower = runs first on the way in, last on the way out). Scope also matters: Global filters wrap Controller filters, which wrap Action-level filters.

builder.Services.AddSingleton<IAuthorizationHandler, MinimumAgeHandler>();

public class MinimumAgeRequirement : IAuthorizationRequirement
{
    public int MinimumAge { get; }
    public MinimumAgeRequirement(int age) => MinimumAge = age;
}

public class MinimumAgeHandler : AuthorizationHandler<MinimumAgeRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        MinimumAgeRequirement requirement)
    {
        var claim = context.User.FindFirst("birthdate");
        if (claim is null) return Task.CompletedTask;

        if (DateTime.TryParse(claim.Value, out var dob))
        {
            var age = DateTime.Today.Year - dob.Year;
            if (DateTime.Today < dob.AddYears(age)) age--;
            if (age >= requirement.MinimumAge) context.Succeed(requirement);
        }
        return Task.CompletedTask;
    }
}

Interview Question

Q: What is the difference between authentication and authorization? How does ASP.NET Core separate them?

A: Authentication answers "who are you?" — it establishes identity (JWT, cookie, API key). Authorization answers "what can you do?" — it checks permissions against the established identity. ASP.NET Core separates them into two middleware: UseAuthentication populates HttpContext.User, then UseAuthorization evaluates policies against it. This separation allows you to swap auth schemes without changing authorization rules.

8JWT Authentication

A JWT consists of three base64url-encoded parts separated by dots: header.payload.signature. The header specifies algorithm (HS256, RS256), payload holds claims (sub, email, roles, exp), signature proves integrity.

builder.Services

    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer           = true,
            ValidIssuer              = builder.Configuration["Jwt:Issuer"],
            ValidateAudience         = true,
            ValidAudience            = builder.Configuration["Jwt:Audience"],
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:SecretKey"]!)),

csharp — Generate + Refresh tokens 
public class JwtTokenService
{
    private readonly IConfiguration _config;
    public JwtTokenService(IConfiguration config) => _config = config;

    public string GenerateAccessToken(ApplicationUser user, IList<string> roles)
    {
        var claims = new List<Claim>
        {
            new(JwtRegisteredClaimNames.Sub,   user.Id.ToString()),
            new(JwtRegisteredClaimNames.Email, user.Email!),
            new(JwtRegisteredClaimNames.Jti,   Guid.NewGuid().ToString()),
            new(JwtRegisteredClaimNames.Iat,
                DateTimeOffset.UtcNow.ToUnixTimeSeconds().ToString()),
        };
        claims.AddRange(roles.Select(r => new Claim(ClaimTypes.Role, r)));

        var key   = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:SecretKey"]!));
        var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

        var token = new JwtSecurityToken(
            issuer:            _config["Jwt:Issuer"],
            audience:          _config["Jwt:Audience"],
            claims:            claims,
            expires:           DateTime.UtcNow.AddMinutes(15),
            signingCredentials: creds);

        return new JwtSecurityTokenHandler().WriteToken(token);
    }

    public string GenerateRefreshToken()
    {
        var bytes = new byte[64];
        RandomNumberGenerator.Fill(bytes);  // cryptographically secure
        return Convert.ToBase64String(bytes);
    }
}

// Refresh endpoint
app.MapPost("/auth/refresh", async (RefreshRequest req, IAuthService auth) =>
{
    var result = await auth.RefreshAsync(req.RefreshToken);
    return result is null
        ? Results.Unauthorized()
        : Results.Ok(result);

Interview Question

Q: How does JWT validation work on the server side?

A: The middleware extracts the token from the Authorization: Bearer <token> header, base64url-decodes the header and payload, re-computes the HMAC signature using the server's secret key (or validates the RSA signature with the public key), compares it to the token's signature, then validates claims: issuer, audience, expiry (exp), not-before (nbf). If all checks pass, a ClaimsPrincipal is created and set on HttpContext.User. No database round-trip needed — that is the stateless advantage of JWTs.

Pitfall

Symmetric key in multi-server deployment — if you use HMAC-SHA256, every instance must share the exact same secret key. A mismatch means some servers reject tokens silently. Prefer RS256 (asymmetric): the issuing server holds the private key; all validating servers only need the public key (shareable via JWKS endpoint).

Pitfall

Storing JWTs in localStorage — XSS can exfiltrate the token. Prefer httpOnly; Secure; SameSite=Strict cookies which are inaccessible to JavaScript. Trade-off: requires CSRF protection.

    private readonly SemaphoreSlim _lock = new(1, 1);
    private readonly HttpClient _http;
    private readonly IConfiguration _config;

    public async Task<string> GetTokenAsync(CancellationToken ct = default)
    {
        if (_token is not null && DateTimeOffset.UtcNow < _expiry.AddMinutes(-1))
            return _token;

        await _lock.WaitAsync(ct);
        try
        {
            var resp = await _http.PostAsync("/connect/token",
                new FormUrlEncodedContent(new Dictionary<string, string>
                {
                    ["grant_type"]    = "client_credentials",
                    ["client_id"]     = _config["OAuth:ClientId"]!,
                    ["client_secret"] = _config["OAuth:ClientSecret"]!,
                    ["scope"]         = "api.read"
                }), ct);

            var token = await resp.Content.ReadFromJsonAsync<TokenResponse>(ct);
            _token  = token!.AccessToken;
            _expiry = DateTimeOffset.UtcNow.AddSeconds(token.ExpiresIn);
            return _token;
        }
        finally { _lock.Release(); }
    }
}
Interview Question

Q: What is the difference between OAuth 2.0 and OpenID Connect?

A: OAuth 2.0 is an authorization framework — it grants a client limited access to a resource on behalf of a user (access tokens). OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0 — it adds authentication via an ID token (JWT) that contains user identity claims (sub, name, email). OAuth alone cannot tell you who the user is; OIDC can.

Interview Question

Q: What is PKCE and why is it necessary?

A: Proof Key for Code Exchange. In Authorization Code flow, a public client (SPA, mobile app) cannot safely store a client secret. Without PKCE, an attacker who intercepts the authorization code can exchange it for tokens. PKCE solves this: the client generates a random code_verifier, hashes it to a code_challenge (SHA-256), sends the challenge with the auth request, and must prove possession of the verifier when exchanging the code. An intercepted code is worthless without the verifier.

Interview Question

Q: What is the difference between liveness and readiness probes in Kubernetes, and how do you implement them?

A: Liveness probe answers "is the process alive?" — if it fails, Kubernetes restarts the pod. It should be a fast check (no external dependencies) to avoid restart loops. Readiness probe answers "is this pod ready to receive traffic?" — if it fails, Kubernetes removes the pod from the Service's load balancer endpoints until it recovers. Map them to separate MapHealthChecks endpoints with different tag predicates: liveness uses Predicate = _ => false (no checks, instant), readiness filters for tagged dependency checks.

11CORS

Browsers enforce the Same-Origin Policy: a script from app.example.com cannot fetch api.example.com unless the server explicitly permits it via CORS headers. ASP.NET Core handles preflight OPTIONS requests automatically once a policy is configured.

csharp — Named policies 
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
        policy
            .WithOrigins("https://app.example.com", "https://admin.example.com")
            .AllowAnyMethod()
            .AllowAnyHeader()
            .AllowCredentials()          // requires WithOrigins, not AllowAnyOrigin
            .WithExposedHeaders("X-Correlation-ID", "X-Total-Count"));

    options.AddPolicy("PublicReadOnly", policy =>
        policy
            .AllowAnyOrigin()       // cannot combine with AllowCredentials
            .WithMethods("GET", "OPTIONS")
            .WithHeaders("Content-Type"));
});

// Apply globally
app.UseCors("Frontend");

// Per-endpoint override in Minimal APIs
products.MapGet("/", GetProducts).RequireCors("PublicReadOnly");

// Per-controller in MVC
[EnableCors("Frontend")]
public class OrdersController : ControllerBase { }

[DisableCors]  // opt-out a specific action
public IActionResult InternalOnly() => Ok();
Pitfall

AllowAnyOrigin() + AllowCredentials() is rejected by browsers (and ASP.NET Core will throw at startup). Credentials (cookies, Authorization header) require an explicit origin list via WithOrigins(). This is a CORS spec restriction, not a framework limitation.

Interview Question

Q: What triggers a CORS preflight request and what does it check?

A: A preflight OPTIONS request is sent by the browser before "non-simple" requests — those using methods other than GET/HEAD/POST, non-standard headers (like Authorization, Content-Type: application/json), or credentials. The browser sends Origin, Access-Control-Request-Method, and Access-Control-Request-Headers. The server must respond with matching Access-Control-Allow-* headers. Only if the preflight succeeds does the browser send the actual request. Preflight responses should be cached via Access-Control-Max-Age.

builder.Services.AddRateLimiter(options =>
{
    // Fixed window
    options.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.Window              = TimeSpan.FromMinutes(1);
        opt.PermitLimit         = 100;
        opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        opt.QueueLimit          = 10;
    });

    // Sliding window
    options.AddSlidingWindowLimiter("sliding", opt =>
    {
        opt.Window           = TimeSpan.FromMinutes(1);
        opt.SegmentsPerWindow = 6;   // 10-second segments
        opt.PermitLimit      = 100;
    });

    // Token bucket — allows bursts
    options.AddTokenBucketLimiter("token-bucket", opt =>
    {
        opt.TokenLimit          = 100;
        opt.TokensPerPeriod     = 20;
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
        opt.AutoReplenishment   = true;
    });

    // Concurrency — cap simultaneous requests
    options.AddConcurrencyLimiter("concurrent", opt =>
    {
        opt.PermitLimit = 10;
        opt.QueueLimit  = 5;
    });

    // Per-user with partition
    options.AddPolicy("PerUser", context =>
        RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: context.User.FindFirstValue(ClaimTypes.NameIdentifier)
                          ?? context.Request.Headers.Host.ToString(),
            factory: _ => new FixedWindowRateLimiterOptions
            {
                Window      = TimeSpan.FromMinutes(1),
                PermitLimit = 60
            }));

    options.OnRejected = async (context, token) =>
    {
        context.HttpContext.Response.StatusCode = 429;
        if (context.Lease.TryGetMetadata(
            MetadataName.RetryAfter, out var retryAfter))
            context.HttpContext.Response.Headers.RetryAfter =
                retryAfter.TotalSeconds.ToString();
        await context.HttpContext.Response
            .WriteAsync("Rate limit exceeded. Please retry later.", token);
    };
});

Interview Question

Q: How does a token bucket differ from a fixed window limiter?

A: Fixed window allows N requests per window and resets hard — a client can send all N at the start of a window, then nothing until the next window. Token bucket fills at a constant rate (e.g., 20 tokens/10 seconds) up to a maximum (100). A client can burst up to the bucket size, then is limited to the fill rate. This is more forgiving for legitimate bursty traffic patterns while still enforcing a steady-state rate. Token bucket is generally preferred for public APIs.

Interview Question

Q: Why use structured logging instead of string interpolation?

A: String interpolation ($"Order {id} created") produces a plain string — unsearchable beyond text. Structured logging ("Order {OrderId} created", id) preserves OrderId as a typed, indexed property in the log store (Seq, ELK, Application Insights). You can then query OrderId = "abc-123" or aggregate order volumes, rather than running slow full-text searches. Additionally, when the log level is disabled, structured logging with LoggerMessage.Define skips the allocation entirely.

csharp — Recurring loop: BackgroundService 
public class OrderProcessorService : BackgroundService
{
    private readonly IServiceScopeFactory _factory;
    private readonly ILogger<OrderProcessorService> _logger;

    public OrderProcessorService(IServiceScopeFactory factory,
        ILogger<OrderProcessorService> logger)
        => (_factory, _logger) = (factory, logger);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("Order processor started");

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await ProcessBatchAsync(stoppingToken);
            }
            catch (OperationCanceledException)
            {
                break;  // graceful shutdown — do not log as error
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Batch processing error. Retrying in 30s.");
            }

            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }

        _logger.LogInformation("Order processor stopped");
    }

    private async Task ProcessBatchAsync(CancellationToken ct)
    {
        // Must create a scope — BackgroundService is a singleton
        using var scope = _factory.CreateScope();
        var repo      = scope.ServiceProvider.GetRequiredService<IOrderRepository>();
        var processor = scope.ServiceProvider.GetRequiredService<IOrderProcessor>();

        var orders = await repo.GetPendingAsync(50, ct);
        foreach (var order in orders)
            await processor.ProcessAsync(order, ct);
    }
}

Interview Question

Q: Why can't you inject IDbContext directly into a BackgroundService?

A: BackgroundService is registered as a singleton (it lives for the application lifetime). DbContext is Scoped — it must be disposed after each unit of work. Injecting Scoped into Singleton is the captive dependency bug. The fix is to inject IServiceScopeFactory and create a new scope per batch/operation, so the DbContext is properly created, used, and disposed within each iteration.

Pitfall

If ExecuteAsync throws before the first await, the exception propagates synchronously and crashes the host at startup. Always wrap the body of ExecuteAsync in a try/catch or ensure the first statement is an await.

SignalR provides real-time, bidirectional communication between server and clients. It negotiates the best available transport: WebSockets → Server-Sent Events → Long Polling.

Interview Question

Q: How do you scale SignalR across multiple servers?

A: Without a backplane, a message sent by server A only reaches clients connected to server A. AddStackExchangeRedis() adds a Redis Pub/Sub backplane: when any server publishes a group message, Redis distributes it to all servers, which forward it to their local connected clients. Azure SignalR Service is the managed alternative — it handles connection management and scaling entirely, so your servers become stateless. For very high scale, Azure SignalR Service is preferred over self-managed Redis.

Interview Question

Q: What transport protocols does SignalR support and how does it choose?

A: SignalR negotiates in order of preference: 1) WebSockets (full-duplex, preferred), 2) Server-Sent Events (server-to-client streaming, HTTP), 3) Long Polling (polling fallback, works everywhere). WebSockets require HTTP/1.1 upgrade support. The client calls /negotiate, the server responds with available transports, and the client picks the best. You can force a specific transport with .withUrl(url, { transport: signalR.HttpTransportType.WebSockets }).

★Quick Reference

Top 10 Interview Questions — Lead Level

  1. Explain the ASP.NET Core request pipeline and middleware order. Pipeline is bidirectional; Use = pass through, Run = terminal, Map = branch. Order: ExceptionHandler → HTTPS → StaticFiles → Routing → CORS → Authentication → Authorization → custom → endpoint.
  2. What is the captive dependency problem? Singleton holding a Scoped service — the scoped instance is never released, shared across requests. Fix: inject IServiceScopeFactory, create a scope per operation.
  3. How does JWT validation work? Extract token → decode header/payload (base64url) → recompute/verify signature → validate claims (iss, aud, exp). Stateless — no DB round trip needed.
  4. Policy-based vs Role-based authorization? Roles are simple strings; policies compose requirements + handlers, are testable, and can use any claim or resource context.
  5. How do you version an API without breaking clients? Keep old version, add new URL segment (/v2/), mark old as Deprecated = true. Monitor traffic; remove only when zero clients remain.
  6. Middleware vs Filters — when to use each? Middleware: any HTTP concern, runs for all requests. Filters: MVC-only, have access to action metadata, model state, and result objects.
  7. Why can't BackgroundService inject IDbContext directly? BackgroundService is singleton; DbContext is scoped. Captive dependency — leaks connection state. Use IServiceScopeFactory.
  8. How do you scale SignalR? Redis backplane (AddStackExchangeRedis) for cross-server messaging, or Azure SignalR Service for fully managed scale-out.
  9. What is PKCE and when is it required? Code verifier/challenge exchange that prevents authorization code interception by public clients (SPA, mobile). Required for Authorization Code flow without client secret.
  10. Difference between IOptions, IOptionsSnapshot, IOptionsMonitor? Singleton+never-reloads vs Scoped+per-request vs Singleton+live-OnChange callback.
