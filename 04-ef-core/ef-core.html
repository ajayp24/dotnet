1Change Tracker

EF Core maintains an internal Change Tracker — a dictionary-like structure that records every entity instance retrieved through a DbContext, along with a snapshot of its original values and its current entity state.

Entity States

StateDescriptionSaveChanges Action
AddedNew entity, not in DB yetINSERT
ModifiedOne or more properties changedUPDATE (changed cols only)
DeletedMarked for removalDELETE
UnchangedRetrieved from DB, nothing modifiedNone
DetachedNot tracked by this contextNone
C#
var order = new Order { Id = 1, Status = "Pending" };

// Attach to context → State: Unchanged
context.Attach(order);

// Modify property → State becomes Modified
order.Status = "Shipped";
Console.WriteLine(context.Entry(order).State); // Modified

// Inspect what changed
var entry = context.Entry(order);
foreach (var prop in entry.Properties)
{
    if (prop.IsModified)
        Console.WriteLine($"{prop.Metadata.Name}: {prop.OriginalValue} → {prop.CurrentValue}");
        // Output: Status: Pending → Shipped
}

SaveChanges() Internals

When SaveChanges() is called, EF Core: (1) calls DetectChanges(), (2) walks all tracked entities comparing current vs original values, (3) generates minimal SQL for only changed columns, (4) executes all SQL in a single implicit transaction, (5) updates snapshots, (6) returns rows affected.

C#
var order = await context.Orders.FindAsync(1);
order.Status = "Shipped";
// Only Status changed → minimal UPDATE generated:
await context.SaveChangesAsync();
SQL
UPDATE Orders SET Status = 'Shipped'
WHERE Id = 1
-- NOT: UPDATE Orders SET Status=..., CreatedAt=..., CustomerId=... (all columns)

DetectChanges() and Performance

C#
// Disable auto-detect during bulk add — huge performance gain
context.ChangeTracker.AutoDetectChangesEnabled = false;
try
{
    foreach (var item in largeList)
        context.Products.Add(item);

    context.ChangeTracker.DetectChanges(); // Once, manually
    await context.SaveChangesAsync();
}
finally
{
    context.ChangeTracker.AutoDetectChangesEnabled = true;
}

// Attach stub entity — update without SELECT round-trip
var stub = new Order { Id = orderId };
context.Attach(stub);       // Unchanged
stub.Status = "Shipped";  // Modified (Status only)
await context.SaveChangesAsync();
// SQL: UPDATE Orders SET Status='Shipped' WHERE Id=@id — no SELECT!
Interview Q — "How does EF Core know what changed?"

EF Core's Change Tracker stores a snapshot of each entity's property values when it is first tracked. When DetectChanges() runs (automatically before SaveChanges), it walks all tracked entities comparing current property values against their stored snapshots. Any property that differs is flagged as modified. EF generates SQL only for modified columns — not a full-column UPDATE. An alternative is notification-based tracking (via INotifyPropertyChanged), which avoids the snapshot scan cost by triggering change events immediately, useful for very high-throughput scenarios.

Lazy Loading — N+1 Problem

Requires UseLazyLoadingProxies() and virtual navigation properties. Deceptively simple to write, catastrophic at scale.

C#
public class Order
{
    public int Id { get; set; }
    public virtual ICollection<OrderItem> Items { get; set; } // virtual = lazy
}

// DANGER: N+1 Problem
var orders = await context.Orders.ToListAsync();
// SQL: SELECT * FROM Orders   ← 1 query

foreach (var order in orders)
{
    Console.WriteLine(order.Items.Count);
    // SQL: SELECT * FROM OrderItems WHERE OrderId = 1  ← fires per order!
    // SQL: SELECT * FROM OrderItems WHERE OrderId = 2
    // SQL: SELECT * FROM OrderItems WHERE OrderId = 3
    // ... N additional queries for N orders = TERRIBLE at scale
}

Eager Loading — .Include() / .ThenInclude()

C#
// Single level — one JOIN query
var orders = await context.Orders
    .Include(o => o.Items)
    .ToListAsync();

// Deep graph — multiple ThenInclude
var orders = await context.Orders
    .Include(o => o.Customer)
    .Include(o => o.Items)
        .ThenInclude(i => i.Product)
            .ThenInclude(p => p.Category)
    .ToListAsync();
SQL
SELECT o.*, c.*, oi.*, p.*, cat.*
FROM   Orders o
LEFT JOIN Customers c   ON c.Id = o.CustomerId
LEFT JOIN OrderItems oi ON oi.OrderId = o.Id
LEFT JOIN Products p    ON p.Id = oi.ProductId
LEFT JOIN Categories cat ON cat.Id = p.CategoryId

Explicit Loading

C#
var order = await context.Orders.FindAsync(orderId);

// Load collection explicitly
await context.Entry(order)
    .Collection(o => o.Items)
    .LoadAsync();

// Load reference explicitly
await context.Entry(order)
    .Reference(o => o.Customer)
    .LoadAsync();

// Load with filter (EF Core 5+)
await context.Entry(order)
    .Collection(o => o.Items)
    .Query()
    .Where(i => i.IsActive)
    .LoadAsync();
// SQL: SELECT * FROM OrderItems WHERE OrderId = @id AND IsActive = 1
Interview Q — "What is the N+1 problem? How do you fix it?"

The N+1 problem occurs when you execute 1 query to load N parent entities, then execute 1 additional query per parent to load related children — resulting in 1 + N database round-trips. It works correctly but scales catastrophically.

  • Fix 1: Eager loading with .Include() — consolidates to a single JOIN query
  • Fix 2: Project with Select — load aggregates in SQL (e.g., o.Items.Count)
  • Fix 3: AsSplitQuery() — separate queries without cartesian explosion
  • Fix 4: Disable lazy loading proxies in production to prevent accidental N+1

3AsNoTracking()

By default, every entity returned by a LINQ query is registered in the Change Tracker. AsNoTracking() skips this entirely — entities are returned as plain objects with no state-tracking overhead.

C#
// Read-only report — ~20–40% faster, no snapshot storage
public async Task<List<ProductDto>> GetCatalogAsync()
{
    return await context.Products
        .AsNoTracking()
        .Include(p => p.Category)
        .Select(p => new ProductDto
        {
            Id           = p.Id,
            Name         = p.Name,
            CategoryName = p.Category.Name,
            Price        = p.Price
        })
        .ToListAsync();
}

// AsNoTrackingWithIdentityResolution — deduplicates objects by identity
// without full tracking overhead (EF Core 5+)
var orders = await context.Orders
    .AsNoTrackingWithIdentityResolution()
    .Include(o => o.Customer)
    .ToListAsync();
// orders[0].Customer and orders[1].Customer are the SAME object reference
// if they share the same CustomerId — prevents object duplication in JOINs

When to Use

ScenarioUse AsNoTracking?
Read-only API endpoints / reportsYES
Display-only viewsYES
CQRS read sideYES
Background read jobsYES
Need to update entity after loadingNO
Need to detect changes laterNO
Interview Q — "What does AsNoTracking() do and when should you use it?"

AsNoTracking() instructs EF Core not to register returned entities in the Change Tracker. This eliminates: the cost of creating property value snapshots, identity map lookups on each row, and entity state management. It is most beneficial for read-only operations — API list endpoints, reports, dashboards — where you never intend to call SaveChanges on the returned entities. The performance gain is typically 20–40% on large result sets. However, if you need to later update or delete the entity through the same context, you need tracked entities or must explicitly re-attach them with context.Attach().

4First() vs Single() vs Find()

Method0 Results2+ ResultsSearches Tracker First?
First()ThrowsReturns firstNo
FirstOrDefault()nullReturns firstNo
Single()ThrowsThrowsNo
SingleOrDefault()nullThrowsNo
Find()nullN/A (PK only)YES
C#
// First() — use when you need first result, entity MUST exist
var latestOrder = await context.Orders
    .OrderByDescending(o => o.CreatedAt)
    .FirstAsync(o => o.CustomerId == customerId);
// Throws InvalidOperationException if no orders for customer

// FirstOrDefault() — entity may or may not exist
var order = await context.Orders
    .FirstOrDefaultAsync(o => o.Id == orderId);
if (order is null) return NotFound();

// Single() — business rule guarantees exactly ONE result
var sub = await context.Subscriptions
    .SingleAsync(s => s.CustomerId == customerId && s.IsActive);
// Throws if 0 or 2+ active subscriptions — good invariant guard

// Find() — PK lookup with Change Tracker cache
var product = await context.Products.FindAsync(productId);
// 1. Checks Change Tracker first (no SQL if already loaded)
// 2. Falls back to: SELECT * FROM Products WHERE Id = @id

// Find() cache demo
var p1 = await context.Products.FindAsync(42); // SQL fired
var p2 = await context.Products.FindAsync(42); // NO SQL — from tracker
Console.WriteLine(ReferenceEquals(p1, p2)); // True
Pitfall — Single() Performance

Single() cannot optimize to SELECT TOP 1 — it must load ALL matching rows from the DB to verify exactly one exists. Use it for small, indexed lookups. On large unfiltered tables, prefer a check with CountAsync() and then First().

Tip — Composite Keys with Find()

For composite primary keys, pass values in the same order they are defined in the model: context.OrderItems.FindAsync(orderId, productId).

5Transactions

Every SaveChanges() call is wrapped in an implicit transaction. Use explicit transactions when you need multiple SaveChanges() calls to be atomic, or when mixing EF with raw ADO.NET.

Explicit Transaction — Money Transfer

C#
public async Task TransferFundsAsync(int fromId, int toId, decimal amount)
{
    await using var tx = await context.Database.BeginTransactionAsync();
    try
    {
        var from = await context.Accounts.FirstAsync(a => a.Id == fromId);
        var to   = await context.Accounts.FirstAsync(a => a.Id == toId);

        if (from.Balance < amount)
            throw new InvalidOperationException("Insufficient funds");

        from.Balance -= amount;
        to.Balance   += amount;

        await context.SaveChangesAsync(); // First save — still in transaction

        context.TransactionLogs.Add(new TransactionLog
        {
            FromAccountId = fromId,
            ToAccountId   = toId,
            Amount        = amount,
            Timestamp     = DateTime.UtcNow
        });

        await context.SaveChangesAsync(); // Second save — still in same transaction

        await tx.CommitAsync(); // Both succeed → commit
    }
    catch
    {
        await tx.RollbackAsync(); // Either fails → rollback both
        throw;
    }
}

Savepoints (EF Core 5+)

C#
await using var tx = await context.Database.BeginTransactionAsync();

await tx.CreateSavepointAsync("BeforeOrder");

try
{
    context.Orders.Add(newOrder);
    await context.SaveChangesAsync();
}
catch
{
    // Rollback only to savepoint — not the full transaction
    await tx.RollbackToSavepointAsync("BeforeOrder");
}

await tx.CommitAsync(); // Commit whatever succeeded
Warning — Distributed Transactions

Avoid System.Transactions.TransactionScope with EF Core. Distributed transactions require MSDTC, are not supported on Linux/macOS, and scale poorly. Use the Outbox Pattern or Saga Pattern for cross-service consistency instead.

6Bulk Insert / Bulk Operations

EF Core 7+ ExecuteUpdate() and ExecuteDelete()

These bypass the Change Tracker entirely and generate direct SQL — no SELECT, no object materialization.

C#
// ExecuteDelete — direct DELETE, no entities loaded
await context.Products
    .Where(p => p.IsDiscontinued && p.LastSaleDate < DateTime.UtcNow.AddYears(-2))
    .ExecuteDeleteAsync();

// ExecuteUpdate — bulk set without loading entities
await context.Products
    .Where(p => p.CategoryId == oldCategoryId)
    .ExecuteUpdateAsync(s => s
        .SetProperty(p => p.CategoryId, newCategoryId)
        .SetProperty(p => p.UpdatedAt, DateTime.UtcNow));
SQL
UPDATE Products
SET    CategoryId = @new, UpdatedAt = @now
WHERE  CategoryId = @old
-- No SELECT. No entity loading. No Change Tracker overhead.

Efficient Bulk Import — 10,000 Records

C#
public async Task ImportProductsAsync(IEnumerable<ProductRow> rows)
{
    context.ChangeTracker.AutoDetectChangesEnabled = false;
    var batch = new List<Product>(500);

    foreach (var row in rows)
    {
        batch.Add(new Product { Name = row.Name, Price = row.Price });

        if (batch.Count == 500)
        {
            context.Products.AddRange(batch);
            await context.SaveChangesAsync();
            context.ChangeTracker.Clear(); // Detach all — prevent memory growth
            batch.Clear();
        }
    }

    if (batch.Any()) { context.Products.AddRange(batch); await context.SaveChangesAsync(); }
    context.ChangeTracker.AutoDetectChangesEnabled = true;
}

// Ultimate option: EFCore.BulkExtensions (NuGet)
await context.BulkInsertAsync(products);
// Single BULK INSERT — ~10x faster than EF batching for large datasets

Raw SQL Methods

C#
// FromSqlRaw — returns tracked entities (use AsNoTracking for reads)
var products = await context.Products
    .FromSqlRaw("SELECT * FROM Products WHERE Price > {0}", minPrice)
    .AsNoTracking()
    .ToListAsync();

// ExecuteSqlRaw — non-query SQL (UPDATE/DELETE/stored procs)
var rows = await context.Database
    .ExecuteSqlRawAsync(
        "UPDATE Products SET Price = Price * 0.9 WHERE CategoryId = {0}",
        categoryId);

// FromSqlInterpolated — safe via FormattableString (no SQL injection)
var products = await context.Products
    .FromSqlInterpolated($"SELECT * FROM Products WHERE CategoryId = {categoryId}")
    .ToListAsync();

7Query Optimization

Projection vs Include — Always Project

C#
// BAD: Loads full entity graph — SELECT * on multiple tables
var orders = await context.Orders
    .Include(o => o.Customer).Include(o => o.Items)
    .ToListAsync();

// GOOD: Project only needed data — minimal network transfer
var summaries = await context.Orders
    .Select(o => new OrderSummaryDto
    {
        OrderId      = o.Id,
        CustomerName = o.Customer.Name,
        TotalItems   = o.Items.Count,
        TotalAmount  = o.Items.Sum(i => i.Price * i.Quantity)
    })
    .ToListAsync();
SQL
SELECT o.Id, c.Name, COUNT(oi.Id), SUM(oi.Price * oi.Quantity)
FROM   Orders o
JOIN   Customers c   ON c.Id = o.CustomerId
LEFT JOIN OrderItems oi ON oi.OrderId = o.Id
GROUP BY o.Id, c.Name

Cartesian Explosion — The Problem

C#
// Includes two collections — generates cartesian product!
var orders = await context.Orders
    .Include(o => o.Items)     // 10 items/order
    .Include(o => o.Payments) // 3 payments/order
    .ToListAsync();
// 100 orders × 10 items × 3 payments = 3,000 rows transferred!

Fix: AsSplitQuery()

C#
var orders = await context.Orders
    .Include(o => o.Items)
    .Include(o => o.Payments)
    .AsSplitQuery()       // 3 separate queries — no cartesian explosion
    .ToListAsync();

// Set globally in OnConfiguring:
optionsBuilder.UseSqlServer(connectionString,
    o => o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));

// Filtered Include (EF Core 5+) — load only active items
var orders = await context.Orders
    .Include(o => o.Items.Where(i => i.IsActive))
    .ToListAsync();
// SQL: LEFT JOIN OrderItems oi ON oi.OrderId = o.Id AND oi.IsActive = 1
SQL
-- AsSplitQuery generates 3 separate queries:
SELECT * FROM Orders                            -- Query 1
SELECT * FROM OrderItems WHERE OrderId IN (...)   -- Query 2
SELECT * FROM Payments   WHERE OrderId IN (...)   -- Query 3
Pitfall — AsSplitQuery Trade-off

AsSplitQuery() uses multiple DB round-trips. If parent result sets are small (e.g., 5 orders with 2 items each), the JOIN overhead is minimal and split queries add unnecessary round-trips. Use split queries when collection sizes are large (5+ children per parent).

8Compiled Queries

Every EF Core LINQ query pays a one-time compilation cost to translate expression trees to SQL. EF caches query plans, but the cache lookup itself has overhead. For hot-path queries (>100 calls/sec), EF.CompileQuery() eliminates this overhead entirely.

C#
public class UserRepository
{
    // Compiled once at startup — expression tree compilation happens ONCE
    private static readonly Func<AppDbContext, int, Task<User?>> _getUserById =
        EF.CompileAsyncQuery((AppDbContext ctx, int userId) =>
            ctx.Users
               .AsNoTracking()
               .Include(u => u.Roles)
               .FirstOrDefault(u => u.Id == userId));

    private static readonly Func<AppDbContext, string, IAsyncEnumerable<Product>> _byCategory =
        EF.CompileAsyncQuery((AppDbContext ctx, string cat) =>
            ctx.Products
               .AsNoTracking()
               .Where(p => p.Category == cat && p.IsActive)
               .OrderBy(p => p.Name));

    private readonly AppDbContext _context;
    public UserRepository(AppDbContext context) => _context = context;

    // No LINQ compilation overhead on each call
    public Task<User?> GetByIdAsync(int id) => _getUserById(_context, id);

    public IAsyncEnumerable<Product> GetByCategory(string cat) =>
        _byCategory(_context, cat);
}
ScenarioWorth Compiling?
> 100 calls/second on same queryYES
Authentication / session lookupYES
Complex queries with many parametersYES
One-off or low-frequency queriesNO
Queries that change shape dynamicallyNO
Tip — Overhead Reduction

Regular EF query overhead per call: ~0.5ms (LINQ parse + cache lookup). Compiled query overhead: ~0.05ms (delegate invoke). At 1,000 calls/sec that's 500ms vs 50ms per second in pure EF overhead — a 10× improvement on hot paths.

9Concurrency

EF Core supports optimistic concurrency — no DB locks during reads. A concurrency token (typically a RowVersion column) is included in UPDATE/DELETE WHERE clauses. If the token changed since you read the record, EF throws DbUpdateConcurrencyException.

RowVersion Setup

C#
public class Product
{
    public int     Id       { get; set; }
    public string  Name     { get; set; } = "";
    public decimal Price    { get; set; }

    [Timestamp]             // SQL Server rowversion — auto-increments on every UPDATE
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}

// Fluent API equivalent
modelBuilder.Entity<Product>()
    .Property(p => p.RowVersion)
    .IsRowVersion()
    .IsConcurrencyToken();

Two Users, One Record — Who Wins?

C#
// User A loads: RowVersion = 0x0001
var productA = await contextA.Products.FindAsync(1);

// User B loads same: RowVersion = 0x0001
var productB = await contextB.Products.FindAsync(1);

// User A saves first
productA.Price = 99.99m;
await contextA.SaveChangesAsync();
// SQL: UPDATE Products SET Price=99.99 WHERE Id=1 AND RowVersion=0x0001
// Succeeds → RowVersion increments to 0x0002

// User B tries to save (stale RowVersion)
productB.Price = 89.99m;
try
{
    await contextB.SaveChangesAsync();
    // SQL: UPDATE Products SET Price=89.99 WHERE Id=1 AND RowVersion=0x0001
    // Fails — 0 rows affected (RowVersion is now 0x0002)
    // EF throws DbUpdateConcurrencyException
}
catch (DbUpdateConcurrencyException ex)
{
    var entry    = ex.Entries.Single();
    var dbVals   = await entry.GetDatabaseValuesAsync(); // User A's values
    var proposed = entry.CurrentValues;                  // User B's proposed

    // Strategy: Client Wins — overwrite DB with User B's version
    entry.OriginalValues.SetValues(dbVals!);
    await contextB.SaveChangesAsync();

    // Strategy: DB Wins — discard User B's changes
    // entry.SetValues(dbVals!);

    // Strategy: Merge — custom field-by-field conflict resolution
}
Interview Q — "How do you handle concurrency in EF Core?"

EF Core uses optimistic concurrency — no locks held during reads, conflict detected at save time. Add a [Timestamp] / rowversion column as the concurrency token. EF automatically includes it in UPDATE WHERE clauses. When 0 rows are affected (token mismatch), EF throws DbUpdateConcurrencyException. Resolution strategies: Last Writer Wins (overwrite), First Writer Wins (discard later change), or Merge (field-by-field comparison and user prompt). Choose based on business requirements — financial systems typically use First Writer Wins; collaborative editors might merge.

Adding Non-Nullable Column to Existing Table

C#
public partial class AddOrderStatusColumn : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        // Step 1: Add with default — backfills existing rows
        migrationBuilder.AddColumn<string>(
            name:         "Status",
            table:        "Orders",
            type:         "nvarchar(50)",
            nullable:     false,
            defaultValue: "Pending");

        // Step 2: Backfill historical rows with meaningful values
        migrationBuilder.Sql(
            "UPDATE Orders SET Status='Completed' WHERE CompletedAt IS NOT NULL");
        migrationBuilder.Sql(
            "UPDATE Orders SET Status='Cancelled' WHERE CancelledAt IS NOT NULL");
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(name: "Status", table: "Orders");
    }
}

Seed Data

C#
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Category>().HasData(
        new Category { Id = 1, Name = "Electronics", CreatedAt = new DateTime(2024, 1, 1) },
        new Category { Id = 2, Name = "Books",       CreatedAt = new DateTime(2024, 1, 1) }
    );
    // HasData requires explicit PK values — generates INSERT in migration
}

// Apply migrations programmatically (production startup)
using var scope = host.Services.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
await db.Database.MigrateAsync(); // Applies any pending migrations
Pitfall — No Automatic Rollback for Failed Migrations
  • Always generate and review the SQL script (Script-Migration) before production deployment
  • Always implement Down() — every migration must be reversible
  • New columns should be nullable or have defaults to allow backward-compatible rolling deployments
  • Use Blue/Green deployment: migrate the DB first, then deploy new app code

DbContext Lifetime

C#
// Correct: Scoped — one DbContext per HTTP request
services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

// High-throughput: DbContextPool — reuse instances, reduce allocations
services.AddDbContextPool<AppDbContext>(options =>

Enable Logging to Diagnose Slow Queries

C#
services.AddDbContext<AppDbContext>(options =>
    options
        .UseSqlServer(connectionString)
        .LogTo(Console.WriteLine, LogLevel.Information)
        .EnableSensitiveDataLogging()   // Shows parameter values (dev only!)
        .EnableDetailedErrors());        // Better exception messages

// Slow query detection via logging tag
var orders = await context.Orders
    .TagWith("GetRecentOrders-v2")  // Tag appears in SQL logs
    .AsNoTracking()
    .Where(o => o.CreatedAt >= DateTime.UtcNow.AddDays(-30))
    .ToListAsync();

Slow vs Fast Query — Side by Side

C#
// ---- SLOW: Common anti-patterns ----
var slow = await context.Orders
    .Include(o => o.Customer)  // Loads 30 Customer columns — only need Name
    .Include(o => o.Items)     // Cartesian explosion with Payments
    .Include(o => o.Payments)  // 3 × 10 × 100 = 3,000 rows
    .ToListAsync()               // No tracking disabled
    .ContinueWith(t => t.Result // Filtering IN MEMORY — should be SQL WHERE
        .Where(o => o.CustomerId == customerId)
        .ToList());

// ---- FAST: All fixes applied ----
var fast = await context.Orders
    .AsNoTracking()                         // No tracking overhead
    .Where(o => o.CustomerId == customerId  // Filter in SQL
        && o.CreatedAt >= DateTime.UtcNow.AddDays(-30))
    .AsSplitQuery()                         // Prevent cartesian explosion
    .Select(o => new OrderSummaryDto       // Project only needed columns
    {
        OrderId     = o.Id,
        Status      = o.Status,
        TotalAmount = o.Items.Sum(i => i.Price * i.Quantity),
        CreatedAt   = o.CreatedAt
    })
    .OrderByDescending(o => o.CreatedAt)
    .Take(50)                               // Paginate
    .ToListAsync();
